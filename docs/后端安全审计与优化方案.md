## 一、审计概述

本次审计覆盖后端全部 **50+ 控制器接口、拦截器链、认证授权体系、文件存储、WebSocket、数据库交互层与配置文件**，重点排查 OWASP Top 10 常见风险（注入、失效认证、越权、敏感信息泄露、安全配置错误等）及生产环境功能缺陷。

**总体评价**：项目安全基础扎实，核心环节（密码加密、SQL 参数化、路径穿越防护、会话固定防护、反序列化白名单）均已正确实现。**主要风险集中在"默认放行"鉴权策略、安全响应头缺失、生产环境配置项默认值偏向开发态**三方面，公网部署前需逐项修复。

## 三、安全漏洞与优化方案

### 高风险

#### H-1 缺少安全响应头（点击劫持 / MIME 嗅探 / HSTS）

**风险等级**：高
**位置**：全局（无任何安全头过滤器）
**现状**：项目中未配置 `X-Frame-Options`、`X-Content-Type-Options`、`Strict-Transport-Security`、`Content-Security-Policy` 等安全响应头。

**影响**：
- **点击劫持**：攻击者可用 iframe 嵌入登录/支付等敏感页面，诱导用户在不知情下完成操作。
- **MIME 嗅探**：浏览器可能将上传的非图片文件按 HTML 解析，导致存储型 XSS（配合文件接口 `/api/file/{id}/{key}` 的 inline 展示）。
- **HSTS 缺失**：首次 HTTP 访问可被中间人劫持降级。

**优化方案**：新增安全头过滤器，对所有响应统一注入：

```java
// 新建 config/SecurityHeadersFilter.java
package com.buguagaoshu.community.config;

import jakarta.servlet.*;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.boot.web.servlet.FilterRegistrationBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.core.Ordered;

@Configuration
public class SecurityHeadersFilter {

    @Bean
    public FilterRegistrationBean<Filter> securityHeadersFilterRegistration() {
        FilterRegistrationBean<Filter> bean = new FilterRegistrationBean<>();
        bean.setFilter((ServletRequest req, ServletResponse res, FilterChain chain) -> {
            HttpServletResponse response = (HttpServletResponse) res;
            response.setHeader("X-Frame-Options", "SAMEORIGIN");
            response.setHeader("X-Content-Type-Options", "nosniff");
            response.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
            response.setHeader("Strict-Transport-Security", "max-age=31536000; includeSubDomains");
            // 文件下载类响应不设 CSP，避免影响 inline 图片展示
            String uri = ((jakarta.servlet.http.HttpServletRequest) req).getRequestURI();
            if (!uri.startsWith("/api/file/")) {
                response.setHeader("Content-Security-Policy", "default-src 'self'; img-src 'self' data: blob:; style-src 'self' 'unsafe-inline'; script-src 'self'; connect-src 'self' ws: wss:;");
            }
            chain.doFilter(req, res);
        });
        bean.addUrlPatterns("/*");
        bean.setOrder(Ordered.HIGHEST_PRECEDENCE);
        return bean;
    }
}
```

### 中风险

#### M-1 权限拦截器"默认放行"，缺少纵深防御

**风险等级**：中
**位置**：`interceptor/PermissionInterceptor.java:36-38`
**现状**：

```java
if (required == null) {
    return true;  // 未标注 @RequirePermission 的方法直接放行
}
```

拦截器采用"默认允许"模式：任何未标注 `@RequirePermission` 的接口方法都会被直接放行，仅靠方法体内手写的 `AuthUtil.requireUser()` / `requireAdmin()` 保护。新增接口时极易遗漏鉴权注解，造成未授权访问。

**已知遗漏案例**：
- `AdminQuestionApiController.deleteQuestion`（`/api/admin/delete/question`）— 无 `@RequirePermission`，普通用户可调用（服务层 `QuestionServiceImpl.deleteQuestion` 有所有权校验兜底，未造成实际越权，但路径语义与 RBAC 链路不一致）。
- `AdminPageApiController.session`（`/api/admin/session`）— 无 `@RequirePermission`（设计意图：路由守卫用，返回空数据，低风险）。

**优化方案**：将 `/api/admin/**` 路径改为"默认拒绝"模式——后台路径下未标注权限的方法一律拦截：

```java
// PermissionInterceptor.java 增加：后台路径默认要求 ADMIN_ACCESS
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    if (!(handler instanceof HandlerMethod handlerMethod)) {
        return true;
    }
    RequirePermission required = AnnotatedElementUtils.findMergedAnnotation(
            handlerMethod.getMethod(), RequirePermission.class);
    if (required == null) {
        required = AnnotatedElementUtils.findMergedAnnotation(
                handlerMethod.getBeanType(), RequirePermission.class);
    }
    String path = request.getRequestURI();
    // 后台路径默认拒绝：未标注权限的 /api/admin/** 一律要求 ADMIN_ACCESS
    if (required == null) {
        if (path.startsWith("/api/admin/")) {
            User user = AuthUtil.currentUser(request);
            if (user == null) {
                throw new CustomizeException(CustomizeErrorCode.NO_LOGIN);
            }
            if (!AuthUtil.hasPermission(user, PermissionCodes.ADMIN_ACCESS)) {
                throw new CustomizeException(CustomizeErrorCode.FORBIDDEN);
            }
        }
        return true;
    }
    // ... 后续校验逻辑不变
}
```

同时为 `AdminQuestionApiController.deleteQuestion` 补充注解（若该接口设计为作者可删自己的帖子，应移出 `/api/admin/` 路径）：

```java
@PostMapping("/api/admin/delete/question")
@RequirePermission(PermissionCodes.ADMIN_QUESTION)  // 补充：仅管理员通过此后台路径删除
public ResultDTO<Object> deleteQuestion(...) { ... }
```

#### M-2 登录限流缺少 IP 维度，无法防御分布式撞库

**风险等级**：中
**位置**：`service/impl/SignInServiceImpl.java:72`
**现状**：

```java
String limitKey = "login:" + email.toLowerCase();  // 仅按 email 限流
```

登录失败锁定仅以 `email` 为维度。攻击者使用代理池对同一账号从不同 IP 暴力破解时，单个 email 的计数仍会触发锁定（这点 OK）；但反过来，攻击者用**大量不同 email + 同一密码**进行撞库时，每个 email 独立计数，永远不会触发锁定。

**优化方案**：增加 IP 维度限流，双维度并行校验：

```java
// SignInServiceImpl.signIn() 内，email 限流之外增加 IP 限流
String ip = IpUtil.getIpAddr(request);
String ipLimitKey = "login:ip:" + ip;
if (rateLimitService.isLocked(limitKey) || rateLimitService.isLocked(ipLimitKey)) {
    throw new CustomizeException(CustomizeErrorCode.TOO_MANY_ATTEMPTS);
}
// ... 密码校验失败时两个 key 都计数
if (!StringUtil.judgePassword(password, user.getPassword())) {
    rateLimitService.recordFailure(limitKey);
    rateLimitService.recordFailure(ipLimitKey);
    throw new CustomizeException(CustomizeErrorCode.SIGN_IN_PASSWORD_ERROR);
}
rateLimitService.reset(limitKey);
rateLimitService.reset(ipLimitKey);
```

建议 IP 维度阈值适当放宽（如 30 次/15 分钟），避免 NAT 网络下正常用户互相影响。

#### M-3 登录失败区分"账号不存在"与"密码错误"，存在用户枚举

**风险等级**：中
**位置**：`exception/CustomizeErrorCode.java` + `SignInServiceImpl.java:80-85`
**现状**：

```java
if (user == null) {
    rateLimitService.recordFailure(limitKey);
    throw new CustomizeException(CustomizeErrorCode.SIGN_IN_EMAIL_ERROR);       // 账号不存在
}
if (!StringUtil.judgePassword(password, user.getPassword())) {
    rateLimitService.recordFailure(limitKey);
    throw new CustomizeException(CustomizeErrorCode.SIGN_IN_PASSWORD_ERROR);    // 密码错误
}
```

账号不存在与密码错误返回**不同的错误码/消息**，攻击者可据此枚举系统中已注册的邮箱。找回密码接口已正确实现防枚举（统一返回成功），但登录接口未对齐。

**优化方案**：统一登录失败消息为"邮箱或密码错误"，不区分两种情况：

```java
private static final CustomizeException INVALID_CREDENTIALS =
        new CustomizeException(CustomizeErrorCode.SIGN_IN_EMAIL_OR_PASSWORD_ERROR);

if (user == null || !StringUtil.judgePassword(password, user.getPassword())) {
    rateLimitService.recordFailure(limitKey);
    rateLimitService.recordFailure(ipLimitKey);  // 配合 M-2 的 IP 维度
    throw new CustomizeException(CustomizeErrorCode.SIGN_IN_EMAIL_OR_PASSWORD_ERROR);
}
```

在 `CustomizeErrorCode` 中合并或新增一个"邮箱或密码错误"的错误码（如复用 `SIGN_IN_EMAIL_OR_PASSWORD_NULL` 或新增 `SIGN_IN_CREDENTIALS_ERROR`），前端文案统一为"邮箱或密码错误"。

#### M-4 JWT payload 含 email / userName，存在信息泄露

**风险等级**：中
**位置**：`util/JwtUtil.java:54-63`
**现状**：

```java
public String createJWT(long id, String userId, String userName, String email, int power, long ttlMillis) {
    JwtBuilder jwtBuilder = Jwts.builder()
            .id(Long.toString(id))
            .subject(userId)
            .claim("roles", power)
            .claim("email", email)           // 敏感信息
            .claim("userName", userName)     // 敏感信息
            .signWith(signingKey());
```

JWT 的 payload 部分仅做 Base64 编码（非加密），任何人拿到 token 都能解码出 `email`、`userName`。虽然 token 是 HttpOnly cookie，JS 无法读取，但仍有以下泄露途径：网络抓包、日志记录、浏览器 cookie 导出。

**优化方案**：JWT 只存用户 ID（用于恢复会话），其余信息从数据库按需查询：

```java
public String createJWT(long id, String ttlMillis) {
    long nowMillis = System.currentTimeMillis();
    return Jwts.builder()
            .id(Long.toString(id))
            .subject("remember-me")
            .issuedAt(new Date(nowMillis))
            .expiration(new Date(nowMillis + ttlMillis))
            .signWith(signingKey())
            .compact();
}
```

`SessionInterceptor.preHandle` 已经在恢复登录态时 `userService.selectUserById(userId)` 查全量用户信息，故移除 email/userName/power claim 不影响功能。`SignInServiceImpl` 创建 token 时也无需再传这些参数。

#### M-5 非图片文件仅后缀校验，可上传伪装文件

**风险等级**：中
**位置**：`repository/FileRepository.java:56-76`
**现状**：

```java
public void validate(MultipartFile file) {
    if (!FileUtil.checkFileType(fileName)) { ... }
    if (ImageUtil.checkFileType(fileName)) {
        // 仅图片做魔数校验
        if (!ImageUtil.isImageContent(file.getBytes())) { ... }
    }
    // 非图片文件（pdf/zip/doc 等）无魔数校验
}
```

图片文件有魔数校验，但 PDF、ZIP、Office 文档等仅校验后缀。攻击者可将恶意 HTML/JS 文件改后缀为 `.pdf` 上传，文件接口对非图片类型以 `attachment` 下载（当前已做），但若未来调整展示方式或攻击者找到 inline 渲染路径，可触发存储型 XSS。

**优化方案**：对所有允许的文件类型补充魔数/文件头校验，至少覆盖主要类型：

```java
// 新建 FileUtil.magicType(fileName, bytes) 返回真实类型
public void validate(MultipartFile file) {
    if (!FileUtil.checkFileType(fileName)) { ... }
    String realType = FileUtil.detectMagicType(file.getBytes());
    String declaredExt = FileUtil.extension(fileName);
    if (!FileUtil.isMagicConsistent(declaredExt, realType)) {
        throw new CustomizeException(CustomizeErrorCode.PARAM_ERROR.getCode(), "文件内容与后缀不一致");
    }
}
```

`FileUtil.detectMagicType` 至少校验：`%PDF`（PDF）、`PK`（ZIP/Office）、`\xFF\xD8`（JPEG）、`\x89PNG`（PNG）、`GIF8`（GIF）等常见文件头。

#### M-6 封禁用户可注册新账号规避封禁

**风险等级**：中
**位置**：`interceptor/BanInterceptor.java:24-30`
**现状**：

```java
private static final Set<String> ALLOWED_PATHS = Set.of(
        "/api/auth/login",
        "/api/admin/login",
        "/api/auth/logout",
        "/api/admin/logout",
        "/api/register"   // 封禁用户可访问注册接口
);
```

封禁拦截器放行 `/api/register`，被封禁用户可重新注册新账号（使用不同邮箱）绕过封禁。若封禁策略依赖邮箱或设备指纹，此放行会导致封禁失效。

**优化方案**：将 `/api/register` 从 `ALLOWED_PATHS` 移除，封禁用户无法注册新账号。若担心误封用户无法恢复，可在注册时检查当前会话是否已登录被封禁账号（`currentUser == null` 时走匿名注册路径，已登录被封禁账号时拒绝）：

```java
private static final Set<String> ALLOWED_PATHS = Set.of(
        "/api/auth/login",
        "/api/admin/login",
        "/api/auth/logout",
        "/api/admin/logout"
        // 移除 /api/register
);
```

> 注意：移除后需确认注册接口的 POST 请求不会被 BanInterceptor 拦截匿名用户（当前 `AuthUtil.currentUser` 对匿名返回 null，`user != null && isBanned` 条件不成立，匿名注册不受影响）。

#### M-7 Swagger / OpenAPI 文档生产环境默认暴露

**风险等级**：中
**位置**：`config/OpenApiConfig.java` + `pom.xml`（引入 `springdoc-openapi`）
**现状**：`/swagger-ui.html` 和 `/v3/api-docs` 默认开放，注释说明"生产可用 `springdoc.api-docs.enabled=false` 关闭"，但 `application.yml` 未配置关闭项。

**影响**：攻击者可获取全部接口路径、参数结构，大幅降低攻击成本。

**优化方案**：在 `application.yml` 中按 profile 控制开关，生产环境关闭：

```yaml
# application.yml（开发态默认开）
springdoc:
  api-docs:
    enabled: true
  swagger-ui:
    enabled: true
```

新建 `application-prod.yml`（或通过环境变量）：

```yaml
# application-prod.yml
springdoc:
  api-docs:
    enabled: false
  swagger-ui:
    enabled: false
```

生产启动时 `--spring.profiles.active=prod`，或 `SPRINGDOC_API_DOCS_ENABLED=false`。

### 低风险 / 生产配置

#### L-1 Cookie Secure 标记默认关闭

**位置**：`application.yml:64-65`
**现状**：`app.cookie.secure: ${COOKIE_SECURE:false}`，token cookie 默认不带 `Secure` 标记，HTTP 下可被中间人截获。

**优化方案**：生产环境设置 `COOKIE_SECURE=true`（需先启用 HTTPS）：

```bash
# 环境变量
export COOKIE_SECURE=true
```

---

#### L-2 Redis 默认无密码

**位置**：`application.yml:30`
**现状**：`password: ${REDIS_PASSWORD:}` 默认空密码。生产环境 Redis 若暴露在内网甚至公网，无密码可被未授权访问/篡改 Session。

**优化方案**：生产环境必须配置 Redis 密码：

```bash
export REDIS_PASSWORD=<强随机密码>
```

并在 `redis.conf` 中设置 `requirepass`，同时绑定 `bind 127.0.0.1` 或内网 IP，关闭公网端口。

---

#### L-3 CORS / WebSocket origin 生产需更新

**位置**：`application.yml:61-62`
**现状**：`app.cors.allowed-origins` 默认仅 `http://localhost:5173`。生产环境前端独立部署时需配置真实域名，否则前端无法访问后端。

**优化方案**：

```bash
export APP_CORS_ALLOWED_ORIGINS=https://your-domain.com,https://www.your-domain.com
```

> ⚠️ **切勿配置为 `*`**：`allowCredentials(true)` + `*` 会被浏览器拒绝，且存在 CSRF 风险。始终使用具体 origin。

---

#### L-4 HTTPS 未启用

**位置**：`application.yml:72-76`（SSL 配置被注释）
**现状**：未启用 HTTPS，Session cookie 和登录凭据明文传输。

**优化方案**：生产环境启用 HTTPS，两种方式：
1. **应用层 SSL**（适合独立部署）：取消注释 `server.ssl` 配置，配置证书。
2. **反向代理终止 SSL**（推荐，Nginx/Caddy 前置）：后端保持 HTTP，Nginx 配置 HTTPS 并转发 `X-Forwarded-Proto`，Spring Boot 配置 `server.forward-headers-strategy=native` 让框架识别 HTTPS。

#### L-5 重置密码接口缺少验证码

**位置**：`controller/api/EmailAuthApiController.java:97-110`
**现状**：`/api/auth/reset-password` 消费 token 后直接重置密码，未要求图形验证码。

**风险**：较低。重置 token 本身是一次性认证因子（30 分钟过期、使用即销毁），已提供足够的身份保证。但增加验证码可防自动化脚本在 token 泄露时批量重置。

**优化方案**（可选加固）：在 `ResetPasswordRequest` 中增加 `captcha` 字段并校验，若产品体验允许。

#### L-6 密码强度无复杂度要求

**位置**：`util/StringUtil.java:18-19` + `dto/RegisterRequest` / `UpdatePasswordRequest`
**现状**：密码规则为"6~30 位字母、数字或常用符号"，无大小写混合、数字+字母等复杂度要求，`123456` 这类弱口令可通过。

**优化方案**：提升最小长度并增加复杂度要求：

```java
// 至少 8 位，须包含字母和数字
public static final String PASSWORD_REGEX =
    "^(?=.*[A-Za-z])(?=.*\\d)[A-Za-z\\d`~!@#$%^&*()+=|{}':;',\\\\\\[\\].<>/?~！@#￥%……&*（）——+|{}【】‘；：”“'。，、？]{8,30}$";
```

同步更新前端校验正则与错误提示。

## 四、功能缺陷

#### F-1 评论缺少用户删除接口

**位置**：`controller/api/CommentApiController.java`
**现状**：仅提供创建评论（`POST /api/comment`）和查询二级评论接口，未见用户删除/编辑自己评论的接口。UGC 平台通常需要用户能管理自己的评论。

**影响**：用户体验缺陷；用户误发评论后无法自行删除，增加管理员运营负担。

**优化方案**：新增 `DELETE /api/comment/{commentId}` 接口，校验评论所有权后软删除：

```java
@DeleteMapping("/api/comment/{commentId}")
@RequirePermission(PermissionCodes.CONTENT_COMMENT_CREATE)
public ResultDTO<Object> deleteComment(@PathVariable Long commentId, HttpServletRequest request) {
    User user = AuthUtil.requireUser(request);
    commentService.deleteComment(commentId, user.getId(), false);  // service 层校验所有权
    siteCache.invalidate(SiteCacheService.HOME);
    return ResultDTO.okOf();
}
```

> 若产品定位不允许用户删评论（仅管理员可删），则此条为设计意图，可忽略。

#### F-2 RateLimitService 在 Redis 不可用时完全放行

**位置**：`component/RateLimitService.java:31-33, 66-68`
**现状**：

```java
public boolean isLocked(String key) {
    try { ... } catch (Exception e) { return false; }  // Redis 故障 → 不锁定
}
public boolean tryAcquire(String key, int max, Duration window) {
    try { ... } catch (Exception e) { return true; }   // Redis 故障 → 全部放行
}
```

Redis 不可用时，登录限流、注册限流、改密限流全部失效。代码注释说明这是"限流是加固手段，不应拖垮主流程"的设计权衡，但生产环境需监控 Redis 健康，避免长时间无防护运行。

**优化方案**：保持现有降级策略（可用性优先），但增加监控告警：

```java
@Component
@Slf4j
public class RateLimitService {
    // ... 现有字段
    private final AtomicInteger redisFailures = new AtomicInteger(0);

    public boolean tryAcquire(String key, int max, Duration window) {
        try {
            // ... 原逻辑
        } catch (Exception e) {
            int count = redisFailures.incrementAndGet();
            if (count % 10 == 1) {  // 避免日志爆炸，每 10 次告警一次
                log.error("Redis 不可用，限流降级放行！累计失败 {} 次，请立即检查 Redis 健康", count);
            }
            return true;
        }
    }
    // isLocked / recordFailure 同理增加告警
}
```

建议配合 APM/告警系统监控 `redisFailures` 指标。

#### F-3 日志可能记录用户敏感操作明文

**位置**：多处 `log.info` / `log.error`
**现状**：部分日志记录了用户 ID 和操作对象（如 `AdminQuestionApiController.resetUserPassword` 记录管理员重置密码），但临时密码 `tempPassword` 通过响应体返回（`Map.of("tempPassword", tempPassword)`）而非日志，这点做得好。

**潜在风险**：登录失败日志若打印 email 参数，可能将用户邮箱写入日志文件。

**优化方案**：审计所有 `log.*` 调用，确保不打印 password、token、验证码等敏感值。对 email 可脱敏（如 `p***@foxmail.com`）。
