# 不挂高数社区 · 后端代码与功能优化建议

> 评估基准：2026-11-15 的 `master` 分支代码快照（Spring Boot 4.1.2 / Java 25 / MyBatis 注解 Mapper / Spring Session + Redis / Vue 3 前后端分离）。
> 评估范围：`src/main/java` 全部 170 个 Java 文件、`databases.sql` 与 `SQL_Upgrade/`、`application.yml`、`pom.xml`，并交叉核对前端 `web/src/api` 的实际调用。
> 阅读对象：项目作者本人。文档默认你已了解项目业务，重点放在「问题在哪、为什么是问题、怎么改、按什么顺序改」。

## 一、现状总览

### 1.1 架构与技术栈

| 层 | 现状 |
| --- | --- |
| Web | Spring MVC 纯 REST（`controller/api/`），无 Thymeleaf；Spring WebSocket/STOMP 聊天室 |
| 持久层 | MyBatis 注解 Mapper（14 个），MySQL 8，HikariCP |
| 会话 | Spring Session + Redis（`SESSION` cookie）；「记住我」用自签 JWT 存 `token` cookie |
| 缓存 | **业务缓存全部是本地 JVM 内存**（`cache/` + `SiteCacheService`），Redis 目前只承载 Session |
| 存储 | 引入了 AWS SDK v2 S3，但**上传调用被注释，实际仍写本地磁盘** |
| 安全 | 无 Spring Security；手写 BCrypt、手写验证码、手写拦截器 |
| 定时 | `@EnableScheduling` + 7 个 `fixedRate` 任务，默认单线程调度器 |

### 1.2 规模与健康度

- 主代码 **170 个 Java 文件**，测试 **1 个**（`CommunityApplicationTests` 是空壳，`contextLoads()` 方法体为空且**缺 `@Test` 注解，根本不会执行**）——有效测试覆盖为 **0**。
- `src/main/resources/static/` 仍保留 **53MB / 2519 个**旧前端文件（Vditor 完整 TS 源码 17MB、assets 15MB、moment 5.6MB、bootstrap 3.7MB），全部进了 git 也会打进 JAR。
- 全项目 **0 处** `jakarta.validation` 注解，参数校验全靠手写 `if`。
- 含真实口令的 `application.yml`（MySQL `root/123456`、S3 `admin/admin`、JWT key）已提交到公开仓库。

### 1.3 已经做得不错的部分（先肯定）

最近四轮升级解决了很多历史问题，本文不再重复建议：

- 数据库已统一 InnoDB + utf8mb4，并按查询模式补了 20 个复合索引（`SQL_Upgrade/001`，幂等可回滚）。
- 计数更新普遍是原子增量（`set commentCount = commentCount + #{n}`），方向正确。
- 所有 Mapper 均用 `#{}` 预编译，**无 SQL 注入**；排序经枚举 switch 选固定 SQL，不拼接。
- 新链路（问题/消息/分类管理）已用统一 `ResultDTO`、会话防越权、TTL 缓存、位置白名单。
- 热度算法（`HotRankingUtil`）多信号加权 + 对数抑制 + 时间衰减，设计合理。
- 分页有上限钳制（`NumberUtils` size∈[5,20]），聊天室做了单窗口限制。

**总体判断**：项目正处在「2019 教程风」向「生产可用」过渡的中间态。新代码质量尚可，旧链路（点赞/关注/后台管理/认证）问题集中。当前最紧迫的不是加功能，而是**堵住安全漏洞、修掉三个实锤 bug、补齐数据一致性兜底**——这些在单机小流量下也许没爆，但一旦公开部署或多实例就会出事。

## 二、问题与优化建议

优先级定义：**P0 = 立即修（安全漏洞 / 功能已坏）**；**P1 = 近期修（一致性 / 性能 / 架构债）**；**P2 = 计划修（质量 / 工程化）**。
每条给出代码位置（相对 `src/main/java/com/buguagaoshu/community/`，SQL 另行标注）。

### 2.1 安全与认证

#### 【P0】S-1 JWT 密钥弱且公开，可伪造任意用户登录态
- 位置：`application.yml:73`（`jwt.key: buguagaoshu`）、`util/JwtUtil.java:56-64`、`interceptor/SessionInterceptor.java:45-49`。
- 问题：密钥是一个公开在 git 里的短字符串，SHA-256 派生只是凑够了 HS256 的 32 字节长度，**熵没有增加**。`SessionInterceptor` 解析 token 后直接 `selectUserById(claims.getId())` 并写入会话，不校验任何其它凭据。任何看过仓库的人都能离线签发 `id=任意用户` 的合法 token，**接管包括管理员在内的任意账号**。
- 建议：
  1. 密钥改为 ≥32 字节随机值，从环境变量/密钥管理注入，**立即轮换**并使旧 token 失效；`application.yml` 只留占位 `${JWT_KEY}`。
  2. 同时把 MySQL、S3 口令移出仓库（见 S-2）。
  3. 中期：记住我 token 改为「服务端随机 opaque token + Redis 存储」，而非自包含 JWT，便于吊销（见 S-6）。

#### 【P0】S-2 敏感配置明文入库
- 位置：`application.yml:8-9`（`root/123456`）、`:81-82`（S3 `admin/admin`）、`:73`（JWT key）；README 指向公开 GitHub 仓库。
- 问题：数据库与对象存储口令、签名密钥全部公开。即使服务在内网，仓库公开即等于凭据泄露。
- 建议：引入 `application-local.yml`（gitignore）或环境变量；提供 `application-example.yml` 模板；用 `git filter-repo` 清理历史中的口令（或至少轮换全部凭据）。生产数据库不要用 root。

#### 【P0】S-3 登录污染单例 JWT 工具，「记住我」影响全站
- 位置：`service/impl/SignInServiceImpl.java:72`（`jwtUtil.setTtl(604800000)`）；`JwtUtil` 是单例 Bean（`config/MyConfig.java:48-50`）。
- 问题：`JwtUtil` 是容器单例，`ttl` 是实例字段。任何一个用户勾选「记住我」，就把**全局** ttl 永久改成 7 天——之后所有不勾选记住我的用户也拿到 7 天 token；并发登录还会互相覆盖。这是典型的「把请求状态写进单例」错误。
- 建议：`createJWT` 增加 `ttl` 参数，TTL 由调用方按本次请求传入，`JwtUtil` 不再持有可变状态：
  ```java
  public String createJWT(long id, String userId, String userName, String email, int power, long ttlMillis) { ... }
  // 调用处：jwtUtil.createJWT(..., rememberMe ? 604_800_000L : 7_200_000L)
  ```

#### 【P0】S-4 改邮箱/昵称接口越权 + 无验证码的密码爆破入口
- 位置：`controller/api/SignUpApiController.java:92-115`（`PATCH /api/update/Email/{id}`）、`:121-145`（`PATCH /api/update/userName/{id}`）。
- 问题：这两个接口从**路径变量**取目标用户 id，只校验「传入密码是否匹配该用户」，**完全不校验当前会话是否就是该用户**，也没有验证码和频率限制。攻击者可对任意 id 反复试密码，响应区分「密码错误/成功」，等于一个**无验证码的在线密码爆破 oracle**；一旦猜中即可改绑邮箱接管账号。
- 建议：目标 id 一律取自会话（`AuthUtil.requireUser(request).getId()`），删除路径 id；敏感操作保留验证码 + 失败计数锁定；改邮箱应走「新邮箱验证链接」而非仅凭旧密码。

#### 【P0】S-5 注册验证码可复用，可批量注册
- 位置：`controller/api/SignUpApiController.java:41-44`；`captcha/CaptchaUtil.java:47-67`（`ver()` 不自动清除）。
- 问题：`ver()` 校验后不清除，由调用方决定何时 `clear()`。登录/改密都正确清除了，**唯独注册只在失败时 clear，成功后验证码仍留在 session**。同一会话 5 分钟内可凭同一验证码无限注册。
- 建议：把「校验即清除」内聚进 `CaptchaUtil.ver()`（校验后立即 `clear`），调用方无需再手动清除，从根上杜绝遗漏；注册另加 IP/会话频率限制。

#### 【P0】S-6 会话与 token 生命周期管理缺失
- 位置：`controller/api/AuthApiController.java:78`（登录）、`:80-84`（cookie）、`:99-113`（登出）；`controller/api/UserUpdateApiController.java:201-241`（改密）。
- 问题（一组）：
  1. **会话固定**：登录直接 `request.getSession().setAttribute(...)`，复用登录前已存在的 session，未 `changeSessionId()`，存在会话固定攻击面。
  2. **token cookie 不安全**：`cookie.setHttpOnly(false)`（JS 可读，XSS 即可窃取）、未设 `Secure`/`SameSite`；token 还在响应体回传（`:88`）并明文存 `onlineUser` 表。
  3. **改密不吊销**：修改密码后不失效旧 token/其它会话，`SessionInterceptor` 也不校验密码版本，被盗 token 在 7 天内持续有效。
  4. **登出不彻底**：前台登出只移除 `user` 属性，**不清 `admin` 属性**、不 invalidate 会话；管理员前台登出后后台仍在线。
- 建议：登录成功后 `request.changeSessionId()`；token cookie 设 `HttpOnly + Secure + SameSite=Lax`（或干脆改用 opaque token）；改密/登出时吊销该用户全部 token 与会话；登出统一 `session.invalidate()`。

#### 【P0】S-7 聊天室无鉴权，可冒充任意用户
- 位置：`config/WebSocketConfig.java:18-28`（无握手/通道拦截器，`setAllowedOriginPatterns("*")`）；`controller/ChatController.java:30-34`、`:61-67`。
- 问题：STOMP 连接不做任何身份校验，`id / sender / image` 全部取自**客户端 payload**。任何人连上 `/ws` 即可冒充任意 userId/昵称发言；`clientToken` 也是客户端自生成，`presence.isActive` 拦不住冒充。`setAllowedOriginPatterns("*")` 还放开了任意来源握手。
- 建议：握手阶段用 `HandshakeInterceptor` 把 HTTP Session 中的用户绑定到 WebSocket attributes；`ChatController` 从 attributes 取身份，**忽略 payload 里的 id/sender**；`allowedOriginPatterns` 收敛为配置的前端域名。

#### 【P1】S-8 权限模型脆弱
- 位置：`util/AuthUtil.java:49-55`（`requireAdmin` 只查会话存在）；`controller/api/AdminApiController.java:50`（仅登录时校验 power）；`AdminQuestionApiController.java:151/182`（power 无范围校验、重置密码硬编码 `123456`）。
- 问题：管理员身份只在登录瞬间校验一次，之后 `requireAdmin` 只看会话里有没有 `admin` 对象。**用户被降权后，旧管理员会话依然有效**；power 可被传入非法值；后台重置密码统一改成 `123456`。
- 建议：`requireAdmin` 每次复核 `userPermission.power`（可加短 TTL 缓存）；power 用枚举校验取值；重置密码改为「生成随机临时密码 + 强制下次修改」或发重置邮件。

#### 【P1】S-9 其它安全加固项
- **CSRF**：会话 cookie 认证 + 无 CSRF token。目前靠 Spring Session 默认 `SameSite=Lax` 兜底，但 `HotCacheApiController.java:46/59/72/85` 用 **GET 做写操作**（刷新/失效缓存），Lax 下顶层导航 GET 会带 cookie，存在 CSRF 面。写操作一律改 POST。
- **反序列化**：`config/HttpSessionConfig.java:24` `enableUnsafeDefaultTyping()` 开启 Jackson 多态默认类型，Redis 一旦被写入恶意 payload 可触发反序列化 gadget。建议改白名单 typing 或会话只存简单类型。
- **IP 伪造**：`util/IpUtil.java:18` 无条件信任 `X-Forwarded-For`，`:39` 用 `length()>15` 截断不兼容 IPv6。应只信任可信代理层并正确解析。
- **限流缺失**：登录、注册、验证码、搜索均无频率限制。建议引入 Bucket4j / Resilience4j 或网关限流。
- **文件上传/下载**：见 2.7 F-2。

### 2.2 实锤功能 bug（已逐一核实）

#### 【P0】B-1 用户自删问题必然 500
- 位置：`controller/api/AdminQuestionApiController.java:104` 调用 `createNotification(question, admin, ...)`，而该分支 `admin == null`；`:246` `if (question.getUserId() == admin.getId())` 对 null 解引用 → **NPE**。
- 影响：普通用户删除自己的问题走的就是这条分支，功能实际已坏（被外层 catch 吞成模糊错误）。
- 建议：自删分支传 `user` 而非 `admin`；`createNotification` 增加 notifier 判空。同时把这段业务逻辑从 Controller 下沉到 Service 并加事务（见 C-2）。

#### 【P0】B-2 取消关注话题，数据库计数反而 +1
- 位置：`service/impl/FollowTopicServiceImpl.java:58`（缓存 -1）vs `:63`（`newClass.setFollowCount(1)`）；`mapper/TagClassMapper.java:58` 是 `followCount = followCount + #{followCount}`。
- 影响：取消关注时缓存减 1、数据库却加 1，**方向相反**，话题关注数越取消越多，缓存与 DB 永久漂移。
- 建议：取消分支 `setFollowCount(-1)`；并补唯一索引防重复（见 C-1）。

#### 【P0】B-3 单例 Service 的分页字段被并发踩踏
- 位置：`service/impl/QuestionServiceImpl.java:50` `private long[] param;`，在 `getQuestionList`（`:85/89/96/102` 等）写入、`getSomeQuestionDto` 读取。
- 影响：`QuestionServiceImpl` 是单例，`param` 是共享可变状态。两个并发请求会互相覆盖分页参数，导致**分页错乱、数据串页**。
- 建议：`param` 改为方法内局部变量，沿调用链传参；Service 中禁止任何请求级可变实例字段。

#### 【P1】B-4 静态 SimpleDateFormat 线程不安全
- 位置：`util/DateFormatUtil.java:33`（静态共享实例）、`:52`（并发 format）。
- 影响：`SimpleDateFormat` 非线程安全，并发下可能抛 `NumberFormatException` 或输出错误日期。
- 建议：改 `DateTimeFormatter`（线程安全）或 `ThreadLocal`；全项目时间处理统一到 `java.time`。

#### 【P1】B-5 通知列表对已删除内容 NPE
- 位置：`service/impl/NotificationServiceImpl.java:124/131`（查 comment/question 后未判空直接取字段）。
- 影响：通知指向的问题/评论被删除后，拉通知列表 NPE。
- 建议：判空并展示「内容已删除」占位。

### 2.3 数据一致性与并发

#### 【P1】C-1 「先查后写」竞态 + 缺唯一索引兜底
- 位置：`ClickLikeServiceImpl:66→86`、`FollowUserServiceImpl:39→50`、`FollowQuestionServiceImpl:41→45`、`FollowTopicServiceImpl:45→55` 都是 select 判重再 insert/delete；`databases.sql` 的 `clickLike`/`followUser`/`followQuestion`/`followTopic` **均无 UNIQUE 约束**（`SQL_Upgrade/001:71` 也只是普通索引）。
- 影响：并发双击/重复请求可插入重复点赞、重复关注，计数随之漂移，且无法靠数据库兜底。
- 建议：
  1. 补唯一索引（先清理存量重复数据）：
     ```sql
     ALTER TABLE clickLike      ADD UNIQUE uk_like (notifier, questionId, commentId);
     ALTER TABLE followUser     ADD UNIQUE uk_follow_user (userId, followUserId);
     ALTER TABLE followQuestion ADD UNIQUE uk_follow_question (userId, followQuestionId);
     ALTER TABLE followTopic    ADD UNIQUE uk_follow_topic (userId, topicId);
     ```
  2. 代码改为「直接 insert，捕获 `DuplicateKeyException` 视为已存在」，或 `INSERT ... ON DUPLICATE KEY`，把判重交给数据库。

#### 【P1】C-2 多表写操作缺事务
- 位置：`FollowQuestionServiceImpl:34-53`（关注表 + 问题 followCount）；`AdminQuestionApiController:64-117/120-147`（删/恢复：循环插通知 + 话题计数 + 改状态，且业务写在 Controller）；`ClassificationAdminApiController:114-128`（改分类 + 批量重命名历史问题）；`OnlineUserServiceImpl:40-46`（先删后插）。
- 影响：中途失败会留下半完成状态（如计数改了、关系没删）。
- 建议：多表写统一加 `@Transactional`（注意现有 `rollbackFor = CustomizeException.class` 是冗余的，它本就是 RuntimeException）；Controller 里的业务下沉到 Service。

#### 【P1】C-3 缓存与数据库双写无补偿
- 位置：`AdvertisementServiceImpl:152/207-243`（DB + 本地缓存双写，仅 `synchronized` 单机锁）；`TagClassServiceImpl:75-78`（先改共享缓存对象再 DB 增量，事务回滚缓存不回滚）。
- 影响：DB 失败/回滚后缓存仍是脏值；`synchronized` 在多实例下失效。
- 建议：以 DB 为准，事务提交后再失效缓存（`TransactionSynchronization.afterCommit`）；缓存只做「失效」不做「双向同步」；容量判断这类强一致逻辑交给数据库唯一约束/乐观锁。

### 2.4 性能

#### 【P1】P-1 列表接口普遍 N+1
- 位置：问题列表 `QuestionServiceImpl:174-185/202-218/342-348`（逐条查用户，部分还查权限 = 2N）；评论 `CommentServiceImpl:164-170/220-225`；通知 `NotificationServiceImpl:106-132`；关注/粉丝 `FollowUserServiceImpl:79-83/98-102`；用户列表 `UserServiceImpl:115-119/133-137`。
- 影响：一页 15 条问题 ≈ 1 + 15×2 次查询；列表越慢、数据库压力越大。
- 建议：先收集 id 集合，用 `WHERE id IN (...)` 一次批量取用户/权限/点赞状态，内存组装。可抽一个 `UserBatchLoader` 复用（当前「去重→循环查→userMap」模板重复了 4 处）。

#### 【P1】P-2 REGEXP 搜索全表扫描 + ReDoS
- 位置：`mapper/QuestionMapper.java:144`（`title regexp #{search} or tag regexp #{search}`）、`mapper/UserMapper.java:190-195`（四字段 regexp OR）；清洗仅删 `+*?`（`DiscoverApiController:192-198`），`()[]{}` 等元字符仍可传入。
- 影响：REGEXP 无法走索引，数据量上来即全表扫描；用户可构造恶意正则触发 MySQL 正则回溯（ReDoS）或制造 SQL 错误。
- 建议：中小规模改 `LIKE '%kw%'` + 全文索引（`FULLTEXT` + `MATCH...AGAINST`，ngram 解析器支持中文）；规模再大上 Elasticsearch/Meilisearch。无论哪种，先对输入做长度与字符白名单校验。

#### 【P1】P-3 offset 深分页退化
- 位置：`QuestionMapper:44/57/169/216` 等手写 `LIMIT #{page},#{size}`（源码多处自注「TODO 优化分页」）。
- 影响：`LIMIT 100000,15` 需扫描并丢弃前 10 万行。
- 建议：列表改游标分页（`WHERE alterTime < #{cursor} ORDER BY alterTime DESC LIMIT n`），配合已有 `idx_questions_status_alter` 索引；后台必须跳页的场景保留 offset 但限制最大页。

#### 【P1】P-4 浏览数同步写放大
- 位置：`QuestionApiController.detail:84` 每次 GET 详情同步 `viewCount+1`。
- 影响：读接口变写接口，热点文章高频 UPDATE 同一行，行锁竞争。
- 建议：浏览数先累加到 Redis（`INCR`），定时批量回写 DB；或异步落库。

#### 【P1】P-5 通知同步单条插入
- 位置：`NotificationMapper:19-22` 仅单条 insert；`AdminQuestionApiController:87-89/140-142` 循环单插；三份 `createNotification` 高度重复（Comment/ClickLike/AdminQuestion）。
- 影响：删一个热帖要给上百评论者逐条插通知，阻塞主流程。
- 建议：抽统一 `NotificationService.createBatch(...)`，Mapper 用 `<foreach>` 批量插入；非关键通知可 `@Async` 异步化。

### 2.5 缓存与定时任务

#### 【P1】T-1 本地缓存的并发与可见性缺陷
- 位置：`cache/AdvertisementCache.java:69-77`（9 个非线程安全 `HashMap` 与定时写并发）；`cache/HotUserCache.java:25`（先 clear 再逐条 add，刷新中读到空榜）；`cache/IndexTopQuestion.java:28-35`（非原子 + 逐 id 查库 N+1）；`service/SiteCacheService.java:52-62`（miss 无锁并发回源、TTL 无抖动）。
- 影响：刷新瞬间读到空/半数据；缓存击穿时大量请求同时回源。
- 建议：榜单类用「构建新集合 → 原子引用替换」（`volatile`/`AtomicReference`），不要原地 clear-add；`SiteCacheService` 回源加 per-key 锁 + TTL 随机抖动；广告缓存换 `ConcurrentHashMap`。

#### 【P1】T-2 定时任务单线程 + 无分布式锁
- 位置：`config/MyConfig.java:53-55`（`ThreadPoolTaskScheduler` 默认池大小 1）；`schedule/*` 全部 `fixedRate`，无 ShedLock/Redisson。
- 影响：7 个任务共用 1 个线程互相阻塞；多实例部署每个任务重复执行（统计重复插入、榜单重复计算）。
- 建议：调度器设 `poolSize`（如 4）；引入 ShedLock（基于 Redis）保证集群内单实例执行；`HotUserTasks:63/68-74` 仍在用旧线性热度公式且逐用户查库，应统一到 `HotRankingUtil` + 批量查询。

#### 【P2】T-3 Redis 仅存 Session，业务缓存未利用
- 现状：花了 Redis 的运维成本，业务缓存却全在本机内存，多实例各自漂移。
- 建议：把热榜、meta、广告等读多写少的缓存迁到 Redis（统一 TTL + 失效广播），本地只留极短 TTL 的二级缓存；为多实例部署铺路。

### 2.6 API 契约与参数校验

#### 【P1】A-1 三套响应格式并存
- 位置：统一 `ResultDTO{code,message,data}`；旧接口 `{success,msg}`（`StringUtil.dealResultMessage:55-60`，AdminApi/AdminQuestionApi/HotCacheApi 等）；文件接口 `FileDTO` 与 Vditor `{code,msg,data}`（`FileApiController:66/115-169`）；`ApiUtilController.getUserIP:36` 返回裸 String。
- 影响：前端 `web/src/api/request.js:105-124` 被迫写 `normalize()` 兼容两套历史格式——契约不一致的成本已经真实转嫁到前端。
- 建议：全部收敛到 `ResultDTO`（Vditor 上传协议除外，它有自己的约定）；旧 `{success,msg}` 接口逐个迁移并下线。

#### 【P1】A-2 错误码混乱 + 业务错误返回 HTTP 200
- 位置：`exception/CustomizeExceptionHandler.java:19-21`（除 401/2003 外业务错误都返回 HTTP 200）；错误码混用枚举 1001~2018、HTTP 风格 400/401/404、散落魔法码 2019（`ClickLikeApiController:47`）、400/409（TopicAdmin/ClassificationAdmin）。
- 建议：业务错误统一用枚举错误码 + 合适的 HTTP 状态（400/403/404/409）；清理魔法数字；补充 `MethodArgumentNotValidException`、`MaxUploadSizeExceededException` 等处理器（目前都落到通用 500）。

#### 【P1】A-3 零参数校验
- 位置：全项目无 `jakarta.validation`；`pom.xml` 未引入 `spring-boot-starter-validation`；`TopicAdmin/ClassificationAdmin` 用 `Map<String,Object>` 收参 + 手写 `parseId`。
- 建议：引入 validation starter，请求体改 DTO + `@Valid`（`@NotBlank/@Size/@Email/@Min` 等），把散落的 `if` 校验收敛为声明式；`Map` 收参改强类型 DTO。

### 2.7 代码质量与遗留清理

#### 【P2】Q-1 死代码 / 学习遗留
- `Test.java`（主代码根下的调试 `main()`，仅打印 `indexOf`）——删除。
- `SignOutApiController`（空类）、`SessionApiController`（「学习 spring-session-jdbc」遗留，会给匿名请求建会话）、`SignInApiController`（旧 `/api/signIn`，前端已改用 `/api/auth/login`，且它不写会话）——删除。
- `cache/TagCache.java`（标签硬编码 + 遗留 `main()`）、`TagClassServiceImpl.getTagClassByType:32-35`（直接 `return null` 未实现）、`StringUtil.jumpWebLangeParameter`（Thymeleaf 跳转遗留）——清理。
- `UserMapper` 注释仍是「学生信息/学号」（拷贝遗留）；`QuestionServiceImpl:74` 作者自注「写的太烂」的 8 分支 if-else——重构为查询条件对象 + 单一动态 SQL。

#### 【P2】Q-2 自造轮子
- `util/BCrypt.java` + `BCryptPasswordEncoder.java` + `PasswordEncoder.java` 整套手抄 jBCrypt/Spring Security，且每次调用 `new` 一个编码器（`StringUtil:15-18`）。建议直接依赖 `spring-security-crypto`（无需引入整个 Spring Security），用单例 `BCryptPasswordEncoder`。
- `NumberUtils` 手写分页、`StringUtil.minus:209-236` O(n²) 差集——可用标准库/集合工具替代。

#### 【P1】F-2 文件存储：S3 迁移半途而废 + 校验不足
- 位置：`FileApiController:90`、`UserUpdateApiController:83` 的 S3 调用被注释，实际 `Files.copy` 写本地磁盘（`:88/156`）；`repository/impl/S3StorageRepositoryImpl.java:89-98` `normalizeKey` 只去前导 `/` 不过滤 `..`，`:75` contentType 直取客户端值；上传仅后缀白名单（`ImageUtil.checkFileType`）无魔数校验；下载 `FileApiController:177-178/232-233` 直接拼路径无规范化校验。
- 影响：本地磁盘存储无法多实例共享、与已引入的 S3 能力割裂；下载端点依赖容器默认拒绝编码斜杠，缺乏纵深防御。
- 建议：二选一并贯彻——要么真正切到 S3（删除磁盘逻辑），要么明确单机定位。上传校验文件魔数（而非仅后缀）、限制大小（`max-request-size: 1024MB` 过大）；下载对路径做 `normalize()` 后校验仍在根目录内；头像 base64 上传的 `b[i]+=256` 是无效操作（`UserUpdateApiController:131-135`）、`Base64MultipartFile.transferTo` 流未关闭——一并修正。

#### 【P2】Q-3 资源泄漏与杂项
- `LogServiceImpl:60` `Files.walk` 流未关闭；`Base64MultipartFile:63-65` 流未关闭——用 try-with-resources。
- 服务端拼「x 分钟前」进 DTO（`DateFormatUtil:38-46`、`QuestionServiceImpl:181`）——不利缓存与国际化，建议回时间戳由前端格式化。
- 硬编码中文遍布错误枚举与提示，无 i18n；status/type 魔法数字（`commentId=-1`、通知 type 3/5、`type<=2/3,4/>=5` 写死 SQL）——用枚举/常量收敛。
- `onlineUser.token varchar(300)`（`databases.sql:68`）可能装不下中文用户名签发的 JWT（payload 含中文经 base64 膨胀后整体可超 300 字符）——扩到 `varchar(512)` 或 `TEXT`。

### 2.8 工程化与可观测性

#### 【P1】E-1 零测试
- 建议：先给「认证/点赞/关注/通知」核心链路补单元测试（Mockito）+ 关键接口集成测试（`@SpringBootTest` + Testcontainers MySQL/Redis）。把空壳 `CommunityApplicationTests` 补上 `@Test`。目标：核心业务行覆盖率先到 50%。

#### 【P2】E-2 构建产物臃肿
- 建议：清理 `src/main/resources/static/` 中旧前端遗留（js/assets/moment/bootstrap 约 44MB），仅保留仍被引用的 `image/`、favicon；前端资源已由 `web/` 独立构建部署。JAR 与仓库体积可大幅下降。

#### 【P2】E-3 缺少交付与运维设施
- 无 API 文档：引入 springdoc-openapi，自动生成 Swagger UI。
- 无 CI：GitHub Actions 跑 `mvn verify` + 前端 lint/build。
- 无容器化：补 Dockerfile + docker-compose（MySQL/Redis/MinIO 一键起）。

### 2.9 数据库设计

#### 【P1】D-1 时间字段用 VARCHAR
- 位置：`databases.sql:34-35`（`users.creationTime/lastTime VARCHAR(19)`）、`userPermission.updateTime`；源码 line 13 自注「TODO 修改时间为 bigint」。
- 影响：无法高效按时间排序/范围查询，字符串比较易错。
- 建议：统一迁 `BIGINT`（毫秒）或 `DATETIME`，与其余表（已用 bigint）对齐。

#### 【P2】D-2 命名与冗余
- 表名大小写混用（`users`/`Questions`/`comment`/`userPermission`/`clickLike`），Linux 下 `lower_case_table_names=0` 时易踩坑；列名 camelCase 与下划线混用。建议统一 snake_case（需配合 Mapper 改动，成本较高，可列为长期项）。
- 反范式冗余副本：`followTopic.topicTitle/topicImage`、`followQuestion.followQuestionTitle`、`notification.commentContent` 缓存了源数据，源改名/删除后即 stale。建议只存外键，展示时 JOIN/批量查。
- `Questions.tag varchar(256)` 逗号分隔标签 + REGEXP 检索：建议拆 `question_tag` 关联表，标签查询走索引（与 P-2 搜索改造配合）。
- `Questions.classification` 存分类名（varchar），重命名需批量回写历史数据；建议存稳定 `code`，展示时映射名称。

### 阶段 1 · 一致性加固与重构（约 2–4 周）

目标：补齐数据一致性兜底，消除主要性能与架构债。

- **唯一索引 + 判重改造**：清理重复数据 → 补 4 张表唯一索引 → 点赞/关注改「insert 捕获重复键」（C-1）。
- **事务补全 + 业务下沉**：FollowQuestion/删恢复问题/分类改名加事务，Controller 业务移入 Service（C-2/B-1）。
- **批量查询消 N+1**：抽 `UserBatchLoader`，问题/评论/通知/关注列表改 IN 批量（P-1）。
- **缓存原子刷新 + 提交后失效**：榜单原子替换、`SiteCacheService` 加锁与抖动、DB 事务提交后再失效缓存（T-1/C-3）。
- **API 契约统一**：收敛到 `ResultDTO` + 枚举错误码 + 合适 HTTP 状态；引入 jakarta.validation（A-1/A-2/A-3）。
- **核心链路测试**：认证/点赞/关注/通知单测 + 集成测试，覆盖率先 50%（E-1）。
- 验收：重复点赞/关注被数据库拒绝；列表接口 SQL 数与页大小无关；`mvn verify` 绿。

### 阶段 2 · 功能演进（约 1–3 月）

目标：补齐社区核心功能短板，提升可用性与可运维性。

- **账号体系**：邮箱验证注册、找回密码（前端 `SignInView.vue:122` 目前是「即将上线」占位，后端无任何邮件能力）、登录限流与异常登录提醒。
- **搜索升级**：FULLTEXT(ngram) 或 Meilisearch 替代 REGEXP，游标分页（P-2/P-3）。
- **通知异步批量化**：统一 NotificationService + foreach 批量 + `@Async`（P-5）。
- **文件存储统一**：真正切 S3（或明确单机），魔数校验、路径规范化、浏览数 Redis 累加（F-2/P-4）。
- **工程化**：springdoc API 文档、Flyway 迁移、Dockerfile + compose、GitHub Actions CI、Micrometer 监控（E-3）。
- **清理瘦身**：删除死代码与 44MB 旧静态资源，BCrypt 换 spring-security-crypto（Q-1/Q-2/E-2）。

### 阶段 3 · 规模化（按需，流量/多实例触发）

- 业务缓存迁 Redis + 失效广播，定时任务加 ShedLock，WebSocket 换外部 broker（Redis/RabbitMQ）支持多实例（T-2/T-3/S-7）。
- 标签拆关联表、时间字段迁 bigint、命名规范统一（D-1/D-2）。
- 读写分离 / 热点数据多级缓存 / 限流熔断网关。
