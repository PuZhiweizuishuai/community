# 不挂高数社区 · 后端数据库增删改查性能优化方案

> 评估基准：2026-11-19 `master` 分支（Spring Boot 4 / Java 25 / MyBatis-Flex 1.11.8 / MySQL 8 / HikariCP / Redis）。
> 评估范围：`mapper/` 全部 28 个 Mapper、`service/impl/` 全部 25 个 ServiceImpl、`controller/api/`、`schedule/`、`cache/`、`component/`、`interceptor/`、`db/migration/` V1~V18。
> 本文聚焦**数据库访问性能**；安全与功能类问题见根目录《后端优化建议.md》（2026-11-15），其中已落地项本文不再重复。

## 二、P0：高收益与正确性问题

### 2.1 标签审核/删除触发 2N 条 SQL 的长事务刷新（站内最大写放大点）

- 位置：`TagAdminServiceImpl.java:197-202`（approve/reject/rename/delete 共用），`QuestionTagServiceImpl.java:138-142`（refreshTagNames）、`:193-198`（refreshUsageCount）。
- 现状：

  ```java
  // TagAdminServiceImpl.refreshQuestionsOfTag
  Set<Long> questionIds = new HashSet<>(questionTagMapper.selectQuestionIdsByTagId(tagId));
  for (Long questionId : questionIds) {
      questionTagService.refreshTagNames(questionId);   // 每帖 1 SELECT + 1 UPDATE
  }
  // QuestionTagServiceImpl.refreshUsageCount
  for (Long tagId : tagIds) {
      tagMapper.updateUsageCount(tagId, tagMapper.countUsage(tagId)); // 每标签 1 COUNT + 1 UPDATE
  }
  ```

- 问题：
  1. 热门标签关联 N 个帖子时，一次审核 = **2N 条 SQL**，全部包在 `@Transactional` 里（`TagAdminServiceImpl:114-186`），长时间持有 questions 多行行锁，阻塞这些帖子的并发更新（评论计数、浏览数回写等）。
  2. `usageCount` 是**先 COUNT 后写绝对值**（`TagMapper.java:49-50`），两个并发发帖事务各自 COUNT 再覆盖写，存在丢失更新——这是全站计数体系里唯一的非原子例外。
- 建议（集合化，一条 SQL 替代一个循环）：

  ```sql
  -- 冗余标签列批量回写（替代逐帖 refreshTagNames）
  UPDATE questions q
  SET q.tag = (
      SELECT GROUP_CONCAT(t.name ORDER BY t.id SEPARATOR ',')
      FROM question_tags qt JOIN tags t ON t.id = qt.tagId
      WHERE qt.questionId = q.questionId AND t.status = 1
  )
  WHERE q.questionId IN (/* 该标签关联的帖子 id，可分批每批 500 */);

  -- 标签使用数原子重算（替代 COUNT+UPDATE 循环，消除覆盖写）
  UPDATE tags t
  SET t.usageCount = (SELECT COUNT(*) FROM question_tags qt WHERE qt.tagId = t.id)
  WHERE t.id IN (...);
  ```

  - `question_tags` 主键 (questionId, tagId) 与 `idx_question_tags_tag(tagId)` 已覆盖上述子查询，无需新索引。
  - 关联帖子极多时按 500/批拆分，避免单条 UPDATE 锁行过多；批间可释放事务。
  - 事务内的 4 个缓存失效同步移到 afterCommit（见 2.3）。
- 预期收益：审核一个关联 1000 帖的标签，从 ~2000 条 SQL/长事务 降为 ~3 条集合化 SQL；`usageCount` 并发安全。

### 2.2 注册三表写无事务（会产生永久无法登录的账号）

- 位置：`controller/api/SignUpApiController.java:109-118`。
- 现状：Controller 里顺序执行 `userService.insertUser` → `userPermissionService.insertUserPermission` → `rbacService.assignRoleByCode`，三步各自独立提交。
- 问题：users 插入成功后若后两步任一失败（连接抖动、死锁），留下**无 user_permissions 行的用户**；登录时 `SignInServiceImpl.java:94-96` 对 `userPermission.getPower()` 解引用 NPE，该账号永久无法登录，且邮箱已被占用无法重新注册。
- 建议：下沉为 `UserService.register(...)` 单方法，`@Transactional(rollbackFor = Exception.class)` 包裹三表写；Controller 只做参数校验与结果转换。这也是「业务写逻辑不放 Controller」的通用原则。
- 预期收益：消除半完成注册；顺带减少一次事务提交往返（3 次 commit → 1 次）。

### 2.3 缓存失效发生在事务提交前（旧值回填窗口）

- 位置（均为 `@Transactional` 方法体内直接 `siteCache.invalidate(...)` / `evict(...)`）：
  - `ReviewServiceImpl.java:244,263`
  - `AdminCommentServiceImpl.java:159,181`
  - `TagAdminServiceImpl.java:125,146,168,184`
  - `TopicModerationServiceImpl.java:200`
  - `UserBanServiceImpl.java:150,165`
  - `RbacServiceImpl.java:163,179,229,257`
- 问题：失效先于 COMMIT 执行，并发读请求在「失效后、提交前」的窗口回源，把**旧数据**重新写进缓存（SiteCache 20~60s TTL、权限/封禁 30s TTL），脏窗口最长可达一个 TTL。审核通过/封禁/降权这类操作对「立即生效」敏感。
- 建议：统一改用项目已有的 afterCommit 模式（`TagClassServiceImpl.refreshCacheAfterCommit:129-140` 是现成模板）：

  ```java
  TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
      @Override public void afterCommit() {
          siteCache.invalidate(SiteCacheService.HOME);
          permissionChecker.evict(userId);
      }
  });
  ```

  可抽一个 `CacheInvalidation.afterCommit(Runnable...)` 工具方法收敛 6 处重复代码。
- 预期收益：缓存与 DB 的最终一致窗口从「最长一个 TTL」缩到毫秒级；无需引入额外中间件。

## 三、P1：明确的性能收益

### 3.1 搜索/相关问题 `SELECT *` 拉回 LONGTEXT 大字段

- 位置：
  - `QuestionMapper.java:170-175`（getRelevantQuestion，`select *`）
  - `QuestionMapper.java:181-182`（fulltextSearchQuestion，`select *`）
  - `UserMapper.java:128-129`（searchUser，`select *`，含 password 列——虽然 `UserServiceImpl.fillPower` 里 `user.clean()` 会剥离，但密码哈希仍每次从 DB 传输到应用）
- 背景：`questions.description` 与 `comments.content` 均为 **LONGTEXT**（`V1__baseline_schema.sql:79,104`）。项目已有 `LIST_COLUMNS`/`LIST_QUERY_COLUMNS`（`QuestionMapper.java:29-39`）专门排除正文，但上述三条查询没有复用。
- 问题：搜索一页 15 条 = 15 篇完整正文（可能每篇几十 KB~MB）从 MySQL 传到应用再丢弃；相关问题 10 条同理。网络带宽、MySQL 内存、JVM GC 三重浪费，且 LONGTEXT  off-page 存储增加随机 IO。
- 建议：
  ```sql
  -- fulltextSearchQuestion / getRelevantQuestion 改为：
  select questionId, userId, title, classification, topicId, fileUrl, viewCount,
         commentCount, likeCount, followCount, tag, isTop, isEssence,
         createTime, alterTime, status, reviewStatus
  from questions where MATCH(title, tag) AGAINST(... IN BOOLEAN MODE) ...
  ```
  直接拼接已有的 `LIST_COLUMNS` 常量即可。`searchUser` 改显式列（排除 password、selfIntroduction 正文，列表只需要 userName/headUrl/simpleSelfIntroduction 等）。
- 预期收益：搜索/相关问题响应体积下降一到两个数量级；这是**改动最小、收益最直观**的一项。

### 3.2 通知未读数 5~6 条 COUNT 打同一张表

- 位置：`controller/api/MessageApiController.java:51-54`（4 条）+ `NotificationServiceImpl.getAllNotification:87-96`（内部再按类型 COUNT）；`NotificationMapper.java:21-71` 提供了 8 个独立 COUNT 方法。
- 问题：打开消息页对 `notifications` 同一 receiver 做 5~6 次 COUNT。虽有 `idx_notification_receiver_type(receiver,type,status)` 索引，但每次都是独立 B+ 树扫描 + 往返。
- 建议：一条聚合替代全部：
  ```sql
  SELECT type, COUNT(*) AS cnt
  FROM notifications
  WHERE receiver = #{receiver} AND status = 0
  GROUP BY type;
  ```
  应用内存归类：type≤2 → 回复，3/4 → 点赞，≥5 → 系统，求和 → 总数。Mapper 增加 `countUnreadGroupByType(receiver)`，8 个旧 COUNT 方法保留给确需单值的场景或逐步下线。
- 附带：`NotificationMapper.readAll:102-106` 的一键已读没有 `status=0` 条件，会把已读行再写一遍（无谓的行锁与 binlog）。补上 `.and(NOTIFICATION.STATUS.eq(0))`。
- 预期收益：消息页 SQL 数 6 → 2（聚合 + 列表）；一键已读写行数大幅下降。

### 3.3 删帖/恢复帖通知：为取评论者 ID 加载整帖评论内容

- 位置：`NotificationServiceImpl.java:238-243`。
- 现状：`selectListByQuery(questionId=?)` 拉回热帖**全部评论实体（含 LONGTEXT content）**，只为 `putIfAbsent(comment.getCommentator(), ...)` 去重。
- 问题：千评热帖删一次 = 上千条 content 大字段进内存，且发生在删帖事务内。
- 建议：
  ```sql
  SELECT DISTINCT commentator FROM comments
  WHERE questionId = #{questionId} AND status = 1 AND reviewStatus = 1;
  ```
  `idx_comment_question_type_status(questionId,type,status)` 可覆盖前缀；如需完全覆盖索引可评估 `(questionId,status,reviewStatus,commentator)`，但通常 DISTINCT 回表量已很小，不必急着加索引。
- 预期收益：删帖事务耗时与内存占用从 O(评论总字数) 降为 O(评论者数)。

### 3.4 管理端聚合统计逐条 COUNT（3 处同模式）

| 位置 | 现状 | 建议 |
| --- | --- | --- |
| `ClassificationAdminApiController.java:69-75` | 每个分类一条 `countQuestionsByClassification(code)` | 一条 `SELECT classification, COUNT(*) FROM questions GROUP BY classification` 内存映射；话题分类同理按 `topics.type` 聚合 |
| `AdvertisementServiceImpl.positionStats:208-216` | 固定 9 个位置 = 9 条 `countActiveByPosition` | 一条 `SELECT position, COUNT(*) FROM advertisements WHERE status=1 AND endTime>#{now} GROUP BY position`（`idx_ad_position_status` 可用） |
| `StorageAdminApiController.java:60` | 每个存储配置一条 `fileCount(storageId)` | 一条 `SELECT storageId, COUNT(*) FROM file_records GROUP BY storageId` |

- 预期收益：分类页/广告位面板/存储页打开时 SQL 数从 N → 1。均为低频管理端，但模式统一、改动小。

### 3.5 RBAC 授权循环单条 INSERT

- 位置：`RbacServiceImpl.java:225-228`（saveRolePermissions）、`:253-256`（saveUserRoles）。
- 现状：`deleteByRoleId` 后 `for (permissionId : ids) insertIgnore(roleId, permissionId)`，一个角色几十个权限点 = 几十条 INSERT 往返，均在事务内。
- 建议：MyBatis-Flex `insertBatch`（项目已在通知/标签关联处用过同款），或注解多值：
  ```sql
  INSERT IGNORE INTO sys_role_permissions(roleId, permissionId) VALUES
  (#{roleId}, #{p1}), (#{roleId}, #{p2}), ...
  ```
  注意保持「先删后插」在同一事务（现状已是）。
- 预期收益：角色保存从 ~50 条 SQL 降为 2 条；事务持锁时间同步缩短。

### 3.6 ViewCountBuffer 回写：逐行 UPDATE + 快照丢失风险

- 位置：`component/ViewCountBuffer.java:64-83`。
- 现状：每分钟 RENAME 快照后 `entries.forEach` 逐条 `increaseViewCount`；两个问题：
  1. 热帖多时 = N 条独立 UPDATE（N 次往返、N 次 commit）。
  2. **可靠性**：`entries()` 读取失败时 `finally` 仍 `delete(snapshotKey)`，这批浏览数永久丢失；单条回写失败也只 log 不补偿。
- 建议：
  1. 合并为单语句（或 JDBC batch）：
     ```sql
     UPDATE questions SET viewCount = viewCount + CASE questionId
         WHEN #{id1} THEN #{delta1} WHEN #{id2} THEN #{delta2} ... END
     WHERE questionId IN (#{id1}, #{id2}, ...);
     ```
     每批 ≤500 个 id，避免 SQL 过长。
  2. 回写失败的快照键**不删除**，改名保留（如 `:failed:<ts>`）并告警，下次 flush 优先重试；或至少把失败 field 重新 HINCRBY 回主缓冲键。
- 预期收益：回写 SQL 数 N → ceil(N/500)；浏览数不再因 Redis 抖动丢失。

### 3.7 发评论链路同一行重复 SELECT 最多 3 次

- 位置：`CommentServiceImpl.java:84 vs 149`（question 查两次）、`:128-132 vs 163/170`（target/root 各查两次）、`:109 → 208-213`（插入后 `getCommentDtoById` 再查刚插入的评论）。
- 问题：审核关闭时一次发评论全链路 ~10 条 SQL，其中 3~4 条是重复读同一行。
- 建议：把已加载的 question/target/root 实体作为参数传入 `publishApprovedComment`；返回 DTO 直接用内存中刚插入的实体组装（自增 id 已由 `@Options` 回填），省掉回查。
- 预期收益：发评论 SQL 数 ~10 → ~6，高频写路径延迟直接下降。

### 3.8 问题详情页无公共缓存（站内最大剩余读压力点）

- 位置：`QuestionApiController.detail:98-155`，每次 GET 约 7~9 条 SQL（question 行 + contents + tags + 作者 + 点赞/关注状态 + 浏览数 pending）。
- 现状：首页/meta/话题页已接 SiteCache，但**详情页与评论分页每次全打 MySQL**。详情数据里「公共部分」（question 行、question_contents、已通过 tags、作者公开信息）与「个性化部分」（当前访问者的点赞/关注状态、受保护段落裁剪）混在一起，导致无法直接缓存。
- 建议：公私分离缓存——
  1. 公共部分按 `question:{id}` 走 `SiteCacheService.get`（TTL 30~60s，写操作 afterCommit 失效，复用 2.3 的统一工具）；
  2. 个性化状态保持实时查（click_likes/follow_questions 单行索引查询，代价极低）；
  3. 评论一级分页可同样按 `question:{id}:comments:{page}` 短 TTL 缓存。
- 预期收益：热帖详情 DB 压力下降 ~80%（7~9 条 → 1~2 条个性化查询）；配合已有 ViewCountBuffer，详情页读路径基本不再压 MySQL。
- 注意：这是本方案里改动面最大的一项，建议放在 P0/P1 小项全部落地后单独迭代，并先补集成测试。

### 3.9 questions 热表冗余索引（写放大）

- 位置：`V1__baseline_schema.sql:92-93` 及后续迁移累积。questions 当前二级索引约 9 个 + 1 个 FULLTEXT：
  `index_question_createTime`、`index_question_alterTime`、`idx_questions_status_alter`、`idx_questions_status_create`、`idx_questions_user_status`、`idx_questions_user_review`、`idx_questions_class_status`、`idx_questions_tag(191)`、`idx_questions_topic`、`ft_questions_title_tag`。
- 分析：
  - `index_question_alterTime` / `index_question_createTime`：所有列表查询都带 `status=1` 条件，已被 `idx_questions_status_alter` / `idx_questions_status_create` 的最左前缀覆盖，单列版大概率无人使用。
  - `idx_questions_tag(191)`：标签筛选已改走 `question_tags` EXISTS（`QuestionMapper.java:197-198`），冗余 tag 列只用于 FULLTEXT 与展示，该前缀索引疑似死索引。
  - 每个二级索引都让 INSERT/UPDATE（尤其 viewCount 高频回写之外的改标签、改状态）多维护一棵 B+ 树。
- 建议：**先验证再删**，不要凭推断直接 DROP：
  ```sql
  -- 运行一段时间（覆盖完整业务周期）后观察：
  SELECT * FROM sys.schema_unused_indexes WHERE object_name = 'questions';
  SELECT index_name, count_read, count_fetch
  FROM performance_schema.table_io_waits_summary_by_index_usage
  WHERE object_name = 'questions' ORDER BY count_read;
  ```
  确认 `count_read=0` 后新增迁移 `V19__drop_redundant_indexes.sql` 删除，并保留回滚脚本（重建索引语句）。comments 表的 `index_comment_createTime` 同法验证。
- 预期收益：questions 写路径索引维护成本下降 ~20-30%，缓冲池占用减少。

## 四、P2：低频路径与工程卫生

### 4.1 先查后写竞态的剩余尾巴（统一改「直接写 + 捕获重复键」）

点赞/关注/标签创建已是正确模式，以下遗漏点按同款补齐：

| 位置 | 现状 | 建议 |
| --- | --- | --- |
| `ContentReportServiceImpl.java:121-129` | SELECT COUNT 判重后 insert，无唯一兜底 | `idx_content_report_duplicate` 是普通索引（status 会变，不能直接唯一化）。改 `INSERT ... SELECT ... WHERE NOT EXISTS(...)` 单语句，或引入「待处理」生成列 + 条件唯一索引 |
| `UserServiceImpl.java:109-114` | 改邮箱先 selectUserByEmail 判重 | 直接 UPDATE，捕获 `DuplicateKeyException` 返回 -1（insertUser:92-97 已有同款，属遗漏） |
| `RbacServiceImpl.java:119-143` | 角色名/编码先查后插，无 catch | 依赖 `uk_sys_role_code/name` + catch |
| `TagAdminServiceImpl.java:162-166` | 标签重命名先查后改 | 依赖 `uk_tags_name` + catch |

### 4.2 其余循环写与重复读（低频，顺手修）

- `AdvertisementTasks.java:67-74,88-94`：过期广告逐条 close → 一条 `UPDATE advertisements SET status=0 WHERE status=1 AND endTime<#{now}`。
- `AdvertisementServiceImpl.java:167-168,191-192`：`@Transactional public synchronized` **锁序错误**——Spring 代理先开事务再进方法体，synchronized 在提交前释放，容量 COUNT 仍可能读到未提交数据。改编程式事务把锁包在外层，或容量判断交给 DB 原子约束。
- `NotificationServiceImpl.java:177-186`：已读先 selectOneById 再 update → 直接 `UPDATE ... SET status=1 WHERE id=? AND receiver=? AND status=0`（顺带补 receiver 条件防越权）。
- `TopicModerationServiceImpl.java:155-158`：卸任先查后删 → 直接 `DELETE WHERE topicId=? AND userId=?`。
- `DiscoverApiController.java:167-168`：tab≠topic 时白查关注话题列表 → 移进条件分支。
- `DiscoverApiController.java:192-193`：moderators() 已批量取吧务，isModerator() 又单查 → 在已取列表中判断。
- `TagAdminServiceImpl.java:127,148,170`：方法首尾各 requireTag(id) 一次 → 复用内存对象。
- `ContentReportServiceImpl.java:200-217`：detail 装配后 `adminCommentService.detail` 内部再全查一遍 → 提供接收预加载数据的重载。
- `CommentServiceImpl.java:196-203`：评论根链最多 10 次逐层 SELECT（兼容历史脏数据）→ 存量修复后移除循环，或一次递归 CTE。
- `TopicAdminApiController.java:99-110`：话题列表 selectAll + 内存 filter/sort 无分页 → 表增大后下推 WHERE/ORDER BY/LIMIT。
- `TopicTagBackfillRunner.java:120-127`：启动回填逐行写 → `JdbcTemplate.batchUpdate`（一次性迁移，量小可不动）。

### 4.3 缓存与内存卫生

- **dashboard 全量 SCAN**：`SiteCacheService.countRedisKeys:212-229` 被 `stats():153` 调用，`AdminOverviewService.systemStatus:88` 每次打开仪表盘都 SCAN 全部 `sitecache:*` 键。建议 stats 结果缓存 30s，或键计数改维护计数器。
- **本地缓存无上限**：`PermissionChecker.java:27`、`UserBanServiceImpl.java:58` 的 ConcurrentHashMap 按 userId 无限增长、过期不清理。建议换 Caffeine（`maximumSize(10_000).expireAfterWrite(30s)`），项目已有 Spring Cache 依赖基础。
- **榜单字段可见性**：`HotQuestionCache.java:20`、`HotTagCache.java:25` 的列表字段**非 volatile**，调度线程重赋值后请求线程可能读到旧引用（HotUserCache/IndexTopQuestion/TagClassCache 已正确用 volatile）。补 volatile 即可。
- **置顶刷新 N+1**：`IndexTopQuestion.java:32-38` 逐 id 调 `questionService.selectQuestionById`（内部 question+user+permission 3 查），上限 3 条影响小，但应复用批量 IN + 列表列轻量装配。
- **空值穿透**：`SiteCacheService.get:104-107` null 结果只进 L1 不进 Redis，多实例下每个实例各自回源一次。可缓存短 TTL 空标记（如 5s），量小可不动。

### 4.4 事务与 SQL 规范统一

- 旧模块约 30 处裸 `@Transactional`（`QuestionServiceImpl:131/466/490`、`CommentServiceImpl:75/147`、`ClickLikeServiceImpl:50`、`ReviewServiceImpl:224/268/317`、Follow* 等）统一补 `rollbackFor = Exception.class`。当前 CustomizeException 是 RuntimeException 风险低，属防御性规范。
- 改密 + 吊销 token 双写（`UserUpdateApiController:154-158`、`EmailAuthApiController:107-108`、`AdminQuestionApiController:124-125`）包成一个事务方法，避免「密码改了旧 token 没吊销」。
- 仍用 offset 分页的查询：`fulltextSearchQuestion`、`selectTopicQuestions`、`searchUser`、通知三个列表、`TagMapper.selectApproved`。分页 size 已被 NumberUtils 钳制、offset 由总数约束，深页风险有限；若未来数据量上来，搜索/话题流优先改游标（首页已有现成模板 `QuestionMapper.java:193-219`）。
- `notifications.commentContent TEXT` 冗余副本（源评论修改/删除后 stale）：长期项，改只存外键、展示时批量查（与 3.3 的 DISTINCT 改造同链路）。
