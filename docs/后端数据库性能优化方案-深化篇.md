## 二、P0

### D-1 详情页把 LONGTEXT 正文从数据库拉回来再扔掉

- 证据链：
  1. `QuestionServiceImpl.java:371`：`selectQuestionById` 用 `questionMapper.selectOneById(id)` —— MyBatis-Flex 按实体**全列**查询，包含 `questions.description LONGTEXT`（`V1__baseline_schema.sql:79`）。
  2. `QuestionApiController.java:143`：详情接口随后 `question.setDescription(null)` —— 正文已改由 `question_contents` 段落表下发（`visibleContents`），description 是**遗留列**。
- 影响：每次详情 GET 都从 MySQL 传输一篇可能几十 KB~MB 的 LONGTEXT（off-page 存储，额外随机 IO），到应用后立刻丢弃。`selectQuestionById` 还有 6+ 个调用方（`IndexTopQuestion`、`ClickLikeServiceImpl`、`CommentServiceImpl`、`FollowApiController`、`QuestionContentServiceImpl` 等），**全部**在白白加载正文。这是第一轮 3.1（搜索 SELECT *）之外更大的一个同类漏洞，且命中站内最高频读路径。
- 建议：
  1. Mapper 增加详情专用投影（复用 `LIST_QUERY_COLUMNS` 思路，按需加 reviewReason 等审核字段）：
     ```java
     default Question selectDetailById(long id) {
         return selectOneByQuery(QueryWrapper.create()
                 .select(QuestionMapper.DETAIL_QUERY_COLUMNS)   // 不含 DESCRIPTION
                 .where(QUESTION.QUESTION_ID.eq(id)));
     }
     ```
  2. `selectQuestionById` 及所有只读调用方切换到投影版；**先确认编辑/更新链路**（`updateQuestion` 仍写 description）是否依赖读回正文，若依赖则仅该路径保留全列。
  3. 长期：description 列已被 question_contents 取代，评估存量迁移后废弃该列（与第一轮 4.4 的 notifications.commentContent 冗余同属「遗留大字段清理」）。
- 预期收益：详情/点赞/评论通知等路径的单次传输量下降一到两个数量级；为第一轮 3.8 的详情公共缓存铺路（缓存里不再存无用的大字段）。

### D-2 JDBC URL 缺批量与预编译缓存参数（insertBatch 收益未兑现）

- 位置：`application.yml:11`
  ```
  jdbc:mysql://...?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai
  ```
- 问题：项目已在通知、标签关联、内容段落多处使用 MyBatis-Flex `insertBatch`（第一轮已表扬），但 Connector/J 在**没有 `rewriteBatchedStatements=true`** 时，JDBC batch 只是逐条发送 INSERT——N 条数据 = N 次网络往返，「批量」只省了 MyBatis 层的开销，没省数据库往返。同时未开启服务端预编译缓存，每条 SQL 每次执行都重新 parse。
- 建议（一次配置，全站批量写受益）：
  ```yaml
  url: jdbc:mysql://.../community?useUnicode=true&characterEncoding=UTF-8&serverTimezone=Asia/Shanghai
       &rewriteBatchedStatements=true
       &useServerPrepStmts=true
       &cachePrepStmts=true
       &prepStmtCacheSize=250
       &prepStmtCacheSqlLimit=2048
  ```
  - `rewriteBatchedStatements=true`：INSERT batch 重写为多值单语句（与第一轮 3.5 RBAC insertBatch 改造叠加生效）；UPDATE batch 重写为多语句一次发送。
  - 注意：重写后 `insertBatch` 的返回行数语义与逐条模式略有差异（成功总数而非逐条），项目现有调用只判成功与否，无兼容问题；`@Options(useGeneratedKeys)` 主键回填在多值 INSERT 下仍正常。
  - `cachePrepStmts` 是**连接级**缓存，与 HikariCP 连接池配合才有效（连接复用时命中），故同时配 `prepStmtCacheSize/SqlLimit`。
- 验证：开启 mapper debug 日志 + MySQL `general_log` 抽样，确认批量插入变成 `INSERT ... VALUES (...),(...),...`；对比通知批量插入耗时。
- 预期收益：所有批量写路径网络往返 N → 1；高频单条 SQL 省去重复 parse。

## 三、P1

### D-3 游标分页每页仍执行全量 COUNT(*)

- 位置：
  - `QuestionServiceImpl.java:298`：`cursorPage` 每页 `setAllCount(countQuestions(...))`，条件含标签 EXISTS 子查询（`listCondition`）。
  - `CommentServiceImpl.java:234`：评论每页先 `selectCountByQuery` 再取页。
  - 搜索（`QuestionServiceImpl:425`、`UserServiceImpl:137`）同样 count + page 双查。
- 问题：游标分页的本意是「翻页成本与深度无关」，但每页附带的全量 COUNT 把成本又拉回 O(符合条件的总行数)；标签筛选的 COUNT 还要对每行做 EXISTS 探测。前端无限滚动场景通常**不需要每页都拿到精确总数**。
- 建议（按场景分级）：
  1. **游标流（首页/话题流）**：总数只在首屏（cursor 为空）计算一次，后续页沿用前端已持有的值；或把 `countQuestions(sort, class, tag, topic)` 的结果按条件键走 `SiteCacheService.get`（TTL 30~60s，写路径 afterCommit 失效——复用第一轮 2.3 工具）。
  2. **评论分页**：`questions.commentCount` 冗余计数已存在且原子维护，一级评论总数可直接读该列（需核对 commentCount 统计口径是否含二级/审核中评论；不一致则修正口径或加 `rootCommentCount`），省掉每页 COUNT。
  3. **搜索**：FULLTEXT count 与 page 各执行一次 MATCH，count 结果按 keyword 短 TTL 缓存；或前端改「加载更多」不显示精确总数。
- 预期收益：列表/评论/搜索翻页 SQL 数直接减 1，且减掉的是最贵的那条。

### D-4 索引与查询条件「差一列」：reviewStatus 不在列表索引内

- 现状对照（索引来自 V1/V2/V11/V17）：

  | 查询 | 条件 | 现有最匹配索引 | 缺口 |
  | --- | --- | --- | --- |
  | 首页游标 `QuestionMapper:193-206` | status=1 **AND reviewStatus=1** + alterTime 游标 | `idx_questions_status_alter(status,alterTime)` | reviewStatus 需回表过滤 |
  | 分类筛选游标（同上 +classification） | +classification=? | `idx_questions_class_status(classification,status)` | 无法提供 alterTime 有序 → 扫描+过滤或 filesort |
  | 评论列表 `CommentServiceImpl:229-244` | questionId+type+status **AND reviewStatus=1** | `idx_comment_question_type_status(questionId,type,status)` | reviewStatus 回表过滤 |
  | 审核列表（ReviewServiceImpl） | reviewStatus+status | `idx_questions_review(reviewStatus,status,questionId)` | 已匹配（好） |

- 分析：`reviewStatus=1` 是几乎所有公开读路径的必备条件，却不在主列表索引里。MySQL 用现有索引取出行后逐行回表判 reviewStatus；待审核内容占比升高时（审核积压），扫描行数放大。分类筛选更糟：`idx_questions_class_status` 只有等值列，取出的行还要按 alterTime 排序/过滤。
- 建议（**替换而非新增**，呼应第一轮 3.9 的索引瘦身，总索引数不增）：
  ```sql
  -- V19（与第一轮冗余索引删除合并为一个迁移，先 EXPLAIN 验证再上线）
  ALTER TABLE questions DROP INDEX idx_questions_status_alter,
      ADD INDEX idx_questions_status_review_alter (status, reviewStatus, alterTime);
  ALTER TABLE questions DROP INDEX idx_questions_class_status,
      ADD INDEX idx_questions_class_status_review_alter (classification, status, reviewStatus, alterTime);
  ALTER TABLE comments DROP INDEX idx_comment_question_type_status,
      ADD INDEX idx_comment_question_type_status_review_time (questionId, type, status, reviewStatus, createTime);
  ```
  - 等值列在前、排序列在后；`ORDER BY alterTime DESC, questionId DESC` 可由**反向索引扫描**满足（InnoDB 二级索引隐含主键，反向扫描时主键序也反转），无需显式 DESC 索引。
  - 评论索引尾部带 createTime 后，默认/最新排序（createTime, commentId）可免 filesort（commentId 为隐含主键同理）；热门排序见 D-5。
  - 上线前对每条查询跑 `EXPLAIN`，确认 `key` 命中新索引、`Extra` 无 `Using filesort`/`Using where` 大量回表；保留旧索引重建语句作回滚。
- 预期收益：公开列表路径从「索引范围扫 + 回表过滤」变为纯索引有序扫描；分类筛选不再退化。

### D-5 评论排序 filesort 与二级回复无上限加载

- 位置：`CommentServiceImpl.java:239-244`（四种排序）、`:254-266`（getTwoLevelCommentByParent）。
- 问题：
  1. BEST_LIKE / BEST_COMMENT 按 likeCount/commentCount 排序，任何 B+ 树索引都无法同时满足「questionId 等值 + 计数排序 + 时间兜底」，必然 filesort。热帖几千条评论时，**每翻一页**都把该帖全部评论取出排序再丢弃 offset 行。
  2. 二级回复查询**没有 LIMIT**：一条热评下所有回复（含 LONGTEXT content）一次拉回。当前业务量小未爆，属隐患。
- 建议：
  1. D-4 的索引已解决默认/最新排序；热门排序二选一：
     - 接受有界 filesort（单帖评论数通常 < 几千），但把 offset 分页改游标（`WHERE (likeCount, createTime, commentId) < (...)` 三元组游标），至少消除深 offset 的重复丢弃；
     - 或为热帖维护「热门评论 Top N」短 TTL 缓存（SiteCache，30s），翻页在缓存快照内进行。
  2. 二级回复加 LIMIT（如 50）+ 「展开更多」游标；或至少 `.limit(0, 200)` 钳制上限。
- 预期收益：热帖评论翻页成本从 O(帖内评论总数) 降为 O(页大小)；二级回复内存有界。

### D-6 批量装配用户仍取全列

- 位置：`UserBatchLoader.java:43`（`selectListByIds` 全列）、`UserServiceImpl.fillPower:169-171` 同款。
- 问题：列表装配只需要 id/userName/headUrl/simpleSelfIntroduction 等展示字段，但 `selectListByIds` 取回 password 哈希、selfIntroduction(500)、likes、birthday、school、major 等全部列，随后 `user.clean()` 剥离密码——**剥离发生在传输之后**。一页 15 条 × 全站所有列表接口，累积浪费可观。
- 建议：Flex `QueryWrapper.select(...)` 显式投影，或 UserMapper 增加 `selectListByIdsForDisplay`：
  ```java
  default List<User> selectDisplayByIds(Collection<Long> ids) {
      return selectListByQuery(QueryWrapper.create()
              .select(USER.ID, USER.USER_NAME, USER.HEAD_URL, USER.SIMPLE_SELF_INTRODUCTION,
                      USER.USER_ID, USER.SEX, USER.SCHOOL, USER.MAJOR, USER.LIKE_COUNT,
                      USER.FOLLOW_COUNT, USER.FANS_COUNT)
              .where(USER.ID.in(ids)));
  }
  ```
  需要完整资料的场景（个人主页、密码校验）保留全列查询。
- 预期收益：所有列表装配的用户查询传输量下降 ~60-80%；密码哈希不再离开数据库（纵深防御）。

### D-7 Lettuce 单共享连接：一次慢 SCAN 阻塞全站会话

- 证据：pom.xml 无 `commons-pool2` → Spring Data Redis 默认 Lettuce **单连接共享**（非阻塞命令线程安全复用）；`SiteCacheService.countRedisKeys:212-229` 在后台仪表盘每次打开时执行 `SCAN sitecache:*` 全键遍历（第一轮 4.3 已列）。
- 本轮补充影响：Session 读写、业务缓存、ViewCountBuffer INCR、分布式锁**全部走同一条连接**。SCAN 遍历期间（键多时可达数十~数百 ms），同连接上的其它命令排队——表现为偶发的登录态读取/缓存延迟尖刺。
- 建议：
  1. 优先落地第一轮 4.3：stats 结果缓存 30s / 键计数改计数器，消灭高频 SCAN（治本）。
  2. 如未来引入更多 Redis 重操作，再考虑引入 commons-pool2 配置 lettuce 池（`spring.data.redis.lettuce.pool.*`）；当前规模不必急。
  3. `RedisMessageListenerContainer`（CacheRedisConfig:45-53）已用独立订阅连接，无需改动。
- 预期收益：消除仪表盘操作对全站 Redis 延迟的连带影响。

### D-8 HikariCP 参数加固

- 位置：`application.yml:14-18`（仅 pool-name/maximum-pool-size=20/minimum-idle=5/connection-timeout=30000）。
- 建议补充：
  ```yaml
  hikari:
    maximum-pool-size: 20        # 保持；需 ≤ MySQL max_connections 的 1/实例数 - 运维余量
    minimum-idle: 5              # 保持
    connection-timeout: 30000    # 保持
    max-lifetime: 1800000        # 30min，主动轮换，避开 MySQL wait_timeout 断连
    keepalive-time: 300000       # 5min 保活探测，防止空闲连接被中间设备掐断
    leak-detection-threshold: 60000  # 连接借出超 60s 告警（定位忘关事务/长事务）
  ```
  - 池大小核算：Web 并发 + 调度池 4（MyConfig:38）+ Flyway/启动任务共用 20；单实例 MySQL 侧 `max_connections` 默认 151 足够，多实例部署时按实例数收敛。
  - `leak-detection-threshold` 与第一轮 2.1 长事务治理互为验证手段：标签刷新长事务若未改好，会直接触发泄漏告警。
- 预期收益：连接生命周期可控、泄漏可观测；无性能损失。

## 四、P2

### D-9 存在性判断与锁定段落的小优化

- `QuestionContentServiceImpl.java:121-127`：`hasCommented` 用 `selectCountByQuery(...) > 0` 判「是否评论过」——COUNT 会数完所有匹配行。改 `selectOneByQuery(...limit 1)` 或 `EXISTS`，命中即返回（`idx_comment_question_type_status` 前缀可用，D-4 后更优）。
- `QuestionContentServiceImpl.visibleContents:64-88`：锁定段落（密码/回复可见）的 content 仍从 DB 取回再在 DTO 置 null。服务端只需 type 即可判锁，可在 SQL 用 `CASE WHEN type IN (...) THEN NULL ELSE content END` 少传正文；收益取决于受保护段落使用率，可选。
- `CommentServiceImpl.java:196-203` 根链回溯（第一轮 4.2 已列）：存量修复后可用一条递归 CTE 替代最多 10 次 SELECT。

### D-10 FULLTEXT 工程细节

- `V4__fulltext_search.sql` 用 ngram 解析器，默认 `ngram_token_size=2`：**单字搜索词不会命中**。若产品需要单字搜索，需评估改 token_size=1（索引体积与噪音上升）或前端最短 2 字提示；当前 `sanitizeFulltextKeyword` 已做布尔模式字符清洗，保持。
- 诊断手段：`SET GLOBAL innodb_ft_aux_table='community/questions'; SELECT * FROM information_schema.INNODB_FT_INDEX_TABLE LIMIT ...` 观察分词与索引规模；`MATCH ... AGAINST` 的 count 与 page 双查按 D-3 缓存。
- FULLTEXT 索引会随 questions 写入同步维护（第一轮 3.9 的写放大来源之一），属搜索能力的必要成本，不建议移除；但冗余的 `idx_questions_tag(191)` 前缀索引（标签筛选已走 question_tags）应验证后删除。

### D-11 外键写开销：已知取舍，保留

- `notifications` 两个 FK 指向 users、`question_tags`/`topic_moderators` 带 CASCADE FK（V1/V17）：每次 INSERT 需对父行加共享锁校验。当前规模开销可忽略，且 CASCADE 保证了删帖/删标签的关联清理正确性——**不建议为性能移除外键**；未来若 notifications 成为写入瓶颈，优先做归档分区而非去约束。

### D-12 可观测性：先看见，再优化

- 现状：pom.xml 无 actuator/micrometer；application.yml 仅留了 mapper debug 注释开关（:94-97）；无慢查询日志配置。
- 建议（低成本三件套）：
  1. **MySQL 慢查询**：`SET GLOBAL slow_query_log=ON; long_query_time=0.5;`（或 my.cnf 持久化），每周回顾 Top SQL——本文所有索引决策都应以慢日志/EXPLAIN 为准。
  2. **performance_schema**：确认 `table_io_waits_summary_by_index_usage` 消费开启，支撑第一轮 3.9 与本轮 D-4 的「验证后删/换索引」。
  3. **actuator + micrometer**：引入 `spring-boot-starter-actuator`，暴露 hikaricp.connections.*、lettuce.command.*、http.server.requests 指标；有 Prometheus 则接，没有则 `/actuator/metrics` 人工巡检。配合第一轮验证手段的「每接口 SQL 计数」形成闭环。
