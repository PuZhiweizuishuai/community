# 实施计划：话题单选（贴吧化）+ 标签多选（带审核）+ 话题吧务体系

> 状态：待评审
> 日期：2026-11-18
> 涉及范围：数据库迁移、后端 API、权限体系、前端发布/浏览/后台页面

---

## 1. 背景与目标

### 1.1 现状问题

- `questions.classification`（提问/讨论/分享）语义上是**帖子类型**，却命名为"分类"。
- 话题（`topics` 表）被当作多选标签使用：帖子通过 `questions.tag` 逗号串与 `topics.title`
  **文本匹配**关联，无外键、无中间表；话题改名/删除即断链。
- 没有真正的话题详情页，点话题卡片只是跳首页 `?tag=标题` 筛选。
- 没有独立的标签模块，发布页标签建议来自硬编码 `TagCache`。

### 1.2 目标模型（贴吧式）

| 维度 | 基数 | 定位 | 说明 |
|---|---|---|---|
| 类型（原"分类"） | 单选 | 帖子形态：提问/讨论/分享 | 已单选，正名 + 存 code |
| 话题 | **单选** | 贴吧的"吧"：发帖必选一个话题 | 外键关联，可关注，有详情页 |
| 标签 | **多选**（≤5） | 吧内细化标记 | 新模块，用户可创建，**审核通过后才公开显示** |
| 话题管理员 | 每话题多人 | 吧主/小吧主 | 管理本话题下帖子 |

### 1.3 已确认的决策

1. **标签创建与审核**（用户确认）：用户发帖时可输入新标签，新标签立即创建为
   `待审核` 状态并与帖子关联，但**不在任何公开页面显示**；管理员审核通过后才显示。
2. **存量帖子归属**（默认方案，可调整）：拆分歧义标签串，取**第一个命中的话题**作为
   `topic_id`，其余命中话题降级为标签；一个都没命中的归入新建默认话题「综合讨论」。
3. **吧务第一期权限**（默认方案，可调整）：删除/恢复本话题帖子、置顶、加精、修改标签。
   审核通过与吧内封禁**不下放**，保留在全局管理员。

## 2. 标签审核机制设计（核心新需求）

### 2.1 标签状态

复用 `ReviewStatusEnum` 的语义（与内容审核一致，降低认知成本）：

| status | 含义 | 公开可见 | 发帖可选/可创建 |
|---|---|---|---|
| 0 PENDING | 待审核 | 否 | 同名复用，不重复创建 |
| 1 APPROVED | 已通过 | 是 | 直接使用 |
| 2 REJECTED | 未通过 | 否 | 允许重新提交（重置为待审核） |

### 2.2 发帖时的标签处理流程

```
用户提交 tagNames: ["Java", "Spring Boot", "我的新标签"]
  对每个名称（trim、统一大小写规则后）：
    ├── 已存在且 APPROVED  → 直接建立 question_tags 关联
    ├── 已存在且 PENDING   → 复用该标签，建立关联（不重复创建）
    ├── 已存在且 REJECTED  → 重置为 PENDING，清空审核字段，建立关联
    └── 不存在             → 创建标签(status=PENDING, createdBy=发帖人)，建立关联
```

- 关联**立即建立**，与标签审核状态解耦：标签一旦审核通过，所有已关联帖子自动显示该标签，
  无需二次操作。
- 标签数量上限沿用 5 个（`StringUtil.judgeTagNumber` 改为校验数组长度）。
- 帖子自身的审核（`reviewStatus`）与标签审核**相互独立**：帖子过审但标签未过审时，
  帖子正常显示、只是不显示该标签。

### 2.3 显示规则

| 场景 | 规则 |
|---|---|
| 帖子列表 / 首页 / 话题页 | 只显示 APPROVED 标签 |
| 帖子详情页（访客） | 只显示 APPROVED 标签 |
| 帖子详情页（作者本人） | 额外显示自己的 PENDING 标签，带「待审核」徽标 |
| 发帖页标签搜索/建议 | 只返回 APPROVED 标签 |
| 热门标签（HotTagCache） | 只统计 APPROVED 标签 |
| 标签筛选 `?tag=名称` | 仅 APPROVED 标签可被筛选命中 |

### 2.4 冗余列同步

`questions.tag` 列**保留为冗余展示列**（原因：V4 建立的全文索引
`ft_questions_title_tag MATCH(title, tag)` 依赖它，删列会破坏搜索）。

- 内容改为：该帖所有 **APPROVED** 标签名按 `,` 拼接。
- 由 `QuestionTagService.refreshTagNames(questionId)` 统一维护，触发时机：
  发帖/编辑帖子、吧务改标签、**标签审核状态变更**（批量刷新所有关联帖子）。
- 标签被拒绝/删除时同样触发刷新，冗余列中不再出现该名称。

### 2.5 后台标签管理

新增权限码 `admin:tag`，新增 `/api/admin/tags` 接口组与后台页面 `/admin/tags`：

- 列表：按状态筛选（默认待审核）、名称搜索、分页；显示使用数、创建人、创建时间。
- 审核：通过 / 拒绝（拒绝需填原因，记录 reviewerId/reviewTime）。
- 维护：重命名（同步刷新关联帖子冗余列）、删除（有关联时先解除关联并刷新）、
  合并（二期可选：把标签 A 的关联转移到 B 后删除 A）。
- 审核结果通过现有通知系统告知标签创建人（复用 `NotificationTypeEnum`，新增标签审核类型）。

## 3. 数据库设计

### 3.1 新表

```sql
-- 标签
CREATE TABLE tags (
  id           bigint PRIMARY KEY AUTO_INCREMENT,
  name         varchar(50) NOT NULL,
  status       int NOT NULL DEFAULT 0 COMMENT '0待审核 1已通过 2未通过（同 ReviewStatusEnum）',
  usageCount   bigint NOT NULL DEFAULT 0,
  createdBy    bigint DEFAULT NULL COMMENT '创建人 userId，存量迁移为 NULL',
  createTime   bigint NOT NULL,
  reviewerId   bigint DEFAULT NULL,
  reviewTime   bigint DEFAULT NULL,
  rejectReason varchar(200) DEFAULT NULL,
  UNIQUE KEY uk_tags_name (name),
  KEY idx_tags_status (status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 帖子-标签关联
CREATE TABLE question_tags (
  question_id bigint NOT NULL,
  tag_id      bigint NOT NULL,
  PRIMARY KEY (question_id, tag_id),
  KEY idx_question_tags_tag (tag_id),
  CONSTRAINT fk_qt_question FOREIGN KEY (question_id) REFERENCES questions(questionId),
  CONSTRAINT fk_qt_tag      FOREIGN KEY (tag_id)      REFERENCES tags(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 话题管理员（吧务）
CREATE TABLE topic_moderators (
  id         bigint PRIMARY KEY AUTO_INCREMENT,
  topic_id   bigint NOT NULL,
  user_id    bigint NOT NULL,
  role       varchar(20) NOT NULL DEFAULT 'moderator' COMMENT 'owner=吧主 moderator=小吧',
  assignedBy bigint NOT NULL COMMENT '任命人 userId',
  createTime bigint NOT NULL,
  UNIQUE KEY uk_topic_moderators (topic_id, user_id),
  KEY idx_topic_moderators_user (user_id),
  CONSTRAINT fk_tm_topic FOREIGN KEY (topic_id) REFERENCES topics(id),
  CONSTRAINT fk_tm_user  FOREIGN KEY (user_id)  REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

### 3.2 questions 表变更

```sql
ALTER TABLE questions
  ADD COLUMN topic_id   bigint DEFAULT NULL AFTER classification,
  ADD COLUMN is_top     int NOT NULL DEFAULT 0 COMMENT '话题内置顶',
  ADD COLUMN is_essence int NOT NULL DEFAULT 0 COMMENT '加精',
  ADD KEY idx_questions_topic (topic_id, status, reviewStatus, alterTime);
-- 回填完成后：
ALTER TABLE questions
  MODIFY COLUMN topic_id bigint NOT NULL,
  ADD CONSTRAINT fk_questions_topic FOREIGN KEY (topic_id) REFERENCES topics(id);
```

- `tag` 列保留为冗余列（见 2.4），全文索引不动。
- `classification` 由名称改为 code：先 `UPDATE questions q JOIN classifications c
  ON c.kind='question' AND c.name=q.classification SET q.classification=c.code`，
  再 `MODIFY classification int NOT NULL`。删除后台改名时批量同步历史数据的补丁逻辑
  （`ClassificationAdminServiceImpl` / `ClassificationMapper.renameQuestionClassification`）。

### 3.3 迁移脚本 V17__topic_single_select_and_tags.sql

执行顺序（单脚本内）：

1. 建 `tags`、`question_tags`、`topic_moderators` 三张新表。
2. `questions` 加 `topic_id`（暂允许 NULL）、`is_top`、`is_essence`。
3. 插入默认话题「综合讨论」（`topics`，type 取现有"休闲灌水"类 code，status=1）。
4. **存量回填**（存储过程或应用侧一次性 Runner，推荐应用侧便于日志与重跑）：
   - 遍历所有 `questions`，按 `,`/`，` 拆分 `tag` 串；
   - 第一个命中 `topics.title` 的作为 `topic_id`；
   - 其余命中话题的名称 + 未命中的自由文本 → 创建为标签（**存量标签直接 APPROVED**，
     createdBy=NULL），建立 `question_tags` 关联；
   - 无命中 → `topic_id` = 默认话题；
   - 重算每个标签 `usageCount`、每个话题 `talkCount`（只统计 status=1 且 reviewStatus=1 的帖子，
     与现有口径一致）；
   - 刷新每帖冗余 `tag` 列。
5. `topic_id` 改 NOT NULL + 外键；`classification` 名称→code 转换。
6. 校验断言：`SELECT COUNT(*) FROM questions WHERE topic_id IS NULL` 必须为 0。

> 回填 Runner 建议做成幂等（按 question_id 判断是否已有关联），失败可重跑。
> 执行方式沿用本机惯例：java 源码模式 + m2 的 mysql-connector-j（无 mysql CLI）。

### 3.4 不动的部分

- `topics` 表结构不变（`type` 继续作为话题分组，即"吧的分类目录"）。
- `follow_topics` 已有 `topicId`，关注关系不受迁移影响；二期去掉对冗余
  `topicTitle/topicImage` 的读取依赖，改为 join 实时取。
- `classifications` 表不变，`kind=question` 组前端文案改"类型"。

### 4.3 权限设计要点

- 全局 RBAC 不动；吧务是**资源范围权限**，用 `topic_moderators` 成员关系判定，
  不新增全局 permission code。
- 所有吧务接口双重校验：`requireModerator(user, topicId)` + 目标帖子归属校验，
  防止跨吧操作。
- 吧主（owner）与小吧（moderator）第一期权限相同，role 字段为二期"吧主可任命小吧"预留。

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| 存量帖子多话题→单选的归属损失 | 降级为标签保留信息；迁移前备份 questions 表；回填日志记录每帖归属决策 |
| 冗余 tag 列与关联表不一致 | 唯一写入入口 refreshTagNames；标签审核变更批量刷新；提供对账脚本 |
| 全文搜索依赖 tag 列 | 保留冗余列，索引不动 |
| 迁移期间线上写入 | 低峰执行；回填 Runner 幂等可重跑；topic_id 先 NULL 后收紧 |
| 吧务越权 | 双重校验（成员关系 + 帖子归属）；所有吧务操作写日志 |
| 标签待审核期间用户重复创建同名 | name 唯一键 + 复用逻辑（2.2），并发下靠唯一键兜底捕获重复后复用 |
| 缓存按 title 寻址的残留调用 | 一期全局 grep `getTagClassMap`/`topicTitle` 清理，编译期删除旧方法暴露遗漏 |

## 8. 验收清单

### A 组（一期）

- [ ] 发帖必选话题（单选），不选被拦截；标签 ≤5。
- [ ] 输入新标签 → 帖子发布成功，公开页面不显示该标签；作者详情页可见「待审核」徽标。
- [ ] 管理员通过标签 → 所有关联帖子立即显示该标签；拒绝 → 不显示且创建人收到通知。
- [ ] 同名待审核标签被第二个用户复用，不产生重复记录。
- [ ] 存量帖子全部有 topic_id；原多话题信息以标签形式保留；talkCount/usageCount 对账一致。
- [ ] 首页 `?topic=`、`?tag=`、类型 code 筛选及叠加均正确；相关问题推荐走关联表。
- [ ] 话题改名后帖子关联、关注关系不断链。
- [ ] 全文搜索（标题+标签）行为不回归。
- [ ] 开启内容审核时：帖子过审 talkCount +1、拒审不计；与标签审核互不影响。

### B 组（二期）

- [ ] 管理员可任命/卸任吧务；吧务列表在话题页展示。
- [ ] 吧务可删除/恢复/置顶/加精本话题帖子、修改标签；操作他话题帖子被 403。
